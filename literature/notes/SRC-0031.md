## Why this source is central

The source gives a recent structured map of automated threat-modelling techniques and connects
method families to concrete tool behavior. It is especially useful for locating the true boundary
of automation:

```text
manually constructed and typed system model
+ threat catalogue
+ selection rules
-> automatically enumerated candidate threats
```

The paper therefore supplies strong comparative evidence for `model_to_candidate_threat`
automation, while leaving `documentation_to_model` outside the automated process.

The WordPress comparison also shows why generated-list size is not a quality measure. Tools attach
threats to different units, use different catalogues and produce different granularity. The same
system may therefore yield lists that cannot be compared by count alone.

The source does not close the model-based security-testing branch of the corpus. Testing,
penetration testing and controls appear in the reviewed literature and references, but the two RQs
and the authors' comparison focus on automated threat modelling.

## Four reading questions

### 1. Research problem and contribution

Manual threat modelling is described as costly, time-consuming and dependent on scarce expert
skills. The paper asks:

- RQ1: which methodologies produce threat models automatically;
- RQ2: which open-source tools support automated threat-modelling methodologies.

The contributions combine three evidence layers:

1. a systematic literature review;
2. detailed descriptions of supporting tools;
3. a common WordPress case implemented in four tools.

The search uses IEEE, Scopus, Springer and ACM, considers English downloadable work from 2012
onward and includes fully or partially automated methods or supporting tools. The selection flow
reported in the narrative is:

```text
465 initial records
-> 115 after abstract screening
-> 55 included after full-text analysis
```

The search table reports 466 rather than 465 initial records. This one-record inconsistency is
preserved as an open issue.

The paper uses the StArt review tool to ingest BibTeX, remove duplicates and support data
collection. It does not report a study-quality assessment, inter-rater agreement or a preregistered
protocol.

### 2. Starting artifacts and representation

The review defines automated threat modelling as security evaluation of an already modelled
system. It therefore assumes that a system representation exists before automated selection begins.

The 55 included studies use:

- DFD: 14;
- extended DFD: 6;
- MACM: 8;
- proprietary graph-based models: 4;
- proprietary architecture models: 6;
- component or asset lists: 7;
- UML-based models: 3;
- developer brainstorming: 2;
- not formally expressed or other minor techniques: 5.

Threat classifications include STRIDE, extended STRIDE, CIA/CIAP, LINDDUN, CAPEC, Prolog rules,
threat trees, threat paths, threat matrices and proprietary languages. STRIDE is the most common,
appearing in 30 reviewed studies.

Threat selection uses labels, element types, relationships, protocols, propagation rules, graph
patterns, model requirements, questionnaires, threat-tree catalogues, generic parameters and other
specialized rules.

The operational input is therefore not arbitrary project documentation. It is a typed and annotated
model whose structure and properties match a tool's catalogue and rule semantics.

### 3. Traceability, change, automation and human role

The core derivation pattern is:

```text
model element or relation
+ element type and properties
+ protocol or relationship role
+ catalogue and rule
-> candidate threat
-> optional mitigation or control
```

Tool-specific variants include:

- Microsoft: relationships between typed components and a proprietary catalogue;
- Threat Dragon: node/edge types and properties, OWASP catalogue, custom threats, status and priority;
- SLA-generator: MACM labels, asset types, relationships, protocols, propagation and NIST controls;
- PyTM: Python model elements, target types, Boolean conditions and CAPEC/MITRE-derived threat data.

Human work remains substantial:

- construct the model;
- select scope and element types;
- provide properties, protocols and controls;
- choose or extend catalogues;
- review long candidate lists;
- reconcile overlaps and different granularity;
- assess plausibility, priority and applicability;
- accept, reject, defer or mitigate candidates.

PyTM can regenerate a threat model after controls are added, which supports repeatable continuous
reruns over a maintained Python model. The paper does not evaluate automatic synchronization with
ordinary documentation or application code, stale detection, update effort or change accuracy.

Traceability exists from model element to generated threat in the described tools, but the paper
does not establish assertion-level provenance back to engineering documents, catalogue-version
provenance, confidence, contradiction handling or independent reviewer rationale.

### 4. Findings, limitations and relationship with DDTA

#### Review findings

Graph and DFD representations dominate. STRIDE is the most common classification. Label-based and
relationship-based selection are the most frequent automation mechanisms.

The paper enumerates nine tools from the SLR and manually adds further tools. The authors state that
the enumeration is incomplete.

#### WordPress comparison

The same simple architecture is recreated in Microsoft, Threat Dragon, SLA-generator and PyTM. The
tools use different asset semantics:

- SLA-generator: nodes;
- Microsoft: arcs/relationships;
- Threat Dragon: nodes and arcs;
- PyTM: all Python model elements.

The final comparison table reports:

```text
SLA-generator: 84 threats, variable granularity
Microsoft:     88 threats, high granularity
Threat Dragon: 30 threats, low granularity
PyTM:          97 threats, high granularity
```

The narrative reports 31 rather than 30 for Threat Dragon. The PyTM section reports 91 threats,
while the comparison reports 97. These inconsistencies remain unresolved.

The tools produce candidate lists at different levels. Microsoft and SLA-generator focus on
different asset scopes, Threat Dragon has fewer available parameters and PyTM includes detailed
CAPEC-like attack patterns that can depend on implementation technology.

The paper explicitly avoids ranking approaches, but its conclusion characterizes Threat Dragon's
model as less complete for the case. This characterization is not backed by an independent ground
truth, precision, recall, false-positive rate or expert-performance experiment.

#### Main limitations

- The review excludes non-English, non-downloadable, manual and domain-specific studies.
- The search starts at 2012.
- The tool list is manually enriched and explicitly incomplete.
- No formal quality assessment or risk-of-bias procedure is reported.
- No inter-rater agreement is reported.
- The WordPress comparison uses one simple case and models adapted manually to each tool.
- No independent reference threat model is supplied.
- Counts and granularity are not normalized.
- No timing, effort, usability, precision, recall or accepted-finding yield is measured.
- Tool and catalogue versions can change after the study horizon.
- Data are available on request rather than through a directly linked public replication package.

## Core definitions

### Automated threat modelling

A fully or partially automated process that evaluates the security of a previously modelled system,
with little or no manual effort in the threat-selection phase.

### Modelling technique

The representation used to describe the target system, including DFD, extended DFD, MACM, another
graph, an architecture model, UML, an asset list or code-based model.

### Threat classification

A vocabulary or structure used to group malicious behavior, such as STRIDE, CIA, LINDDUN, CAPEC,
threat tree, threat path or a custom language.

### Threat-selection technique

The mapping logic that decides which catalogue threats apply to which model elements, using labels,
types, relationships, protocols, properties, propagation, patterns, requirements or parameters.

### Threat modelling as code

A purpose-built executable architecture model, exemplified by PyTM's Python objects, from which
views and candidate threats are generated. It is not equivalent to analysing arbitrary application
source code.

## Tool comparison

### Microsoft Threat Modeling Tool

- graphical proprietary DFD-like model;
- threats associated primarily with typed component relationships;
- proprietary threat and mitigation catalogues;
- broad stencil vocabulary;
- HTML report.

### OWASP Threat Dragon

- graphical DFD;
- nodes and flows are assets;
- component and flow properties activate catalogue threats;
- supports custom threats, open/mitigated status and priority;
- suggests mitigations.

### SLA-generator

- graphical MACM stored in Neo4j;
- nodes carry labels, asset types and properties;
- relationships include `uses`, `hosts`, `provides` and `connects`;
- threat catalogue includes asset type, relation, protocol, role, behavior, STRIDE and compromised asset;
- supports propagation and NIST SP 800-53 control suggestions.

### PyTM

- Python architecture model authored by the threat modeller;
- generates DFD, sequence diagram and threat report;
- threat target and Boolean condition decide applicability;
- supports custom threats and model controls;
- can rerun after controls change;
- some results are technology-specific.

## Traceability, change, automation and human role

### Traceability present

```text
model version
-> element / relation
-> type and properties
-> catalogue entry and selection rule
-> candidate threat
-> mitigation or control
```

The paper describes most of this chain at tool level but does not govern version identifiers or
source-document provenance.

### Change

PyTM supports updating controls and regenerating candidates. No evaluated mechanism keeps model,
documents, implementation and threat dispositions synchronized.

### Automation

Automation is strongest in catalogue selection and report generation. Model construction,
semantics, catalogue maintenance, validation and prioritization remain human responsibilities.

### Human review

The long lists generated even for the simple case require expert review. The paper states that
asset-versus-relationship listing preferences remain subjective and does not measure reviewer
agreement or accepted-finding yield.

## Documentation-first classification

### Classification

`model_required`

Project documentation may inform the human modeller, but it is not the direct input evaluated by
the reviewed automation. A typed model compatible with tool rules is required.

### Nine documentation-first fields

1. Input and quality: typed model, annotations, catalogue and rules; document quality is outside scope.
2. Compatibility: `model_required`.
3. Intermediate representation: DFD, graph, MACM, UML, asset list or purpose-built code model.
4. Procedure: model construction followed by catalogue/rule matching and human review.
5. Output: candidate threats, classifications, mitigations and sometimes controls/risk data.
6. Provenance, uncertainty, review: element-to-threat links exist; document provenance, confidence and review rationale are not governed.
7. Evolution/change: PyTM supports rerun after control changes; cross-artifact synchronization is not evaluated.
8. Evaluation/evidence: 55-study SLR plus one illustrative WordPress comparison.
9. Thesis use: automation landscape and plugin boundary; not proof of tool correctness or completeness.

## Directly supported

- Automated threat selection generally assumes a pre-existing typed model.
- DFD and graph-based representations dominate the reviewed automated methods.
- STRIDE is the most common threat classification in the corpus.
- Labels and relationships are frequent threat-selection mechanisms.
- Properties, protocols, roles, propagation and graph rules can make selection more specific.
- Different tools attach threats to different model units and use different granularity.
- Threat-list counts cannot be interpreted without model and catalogue context.
- PyTM exemplifies repeatable threat modelling as code rather than source-code analysis.
- Human modelling and review remain necessary.
- The tool enumeration is incomplete and time-sensitive.

## Not supported

- The reviewed tools identify every applicable threat.
- More generated threats indicate a better tool.
- The generated WordPress lists are correct or complete.
- Threat Dragon is generally inferior to the other tools.
- Automation eliminates security experts.
- The tools derive their model from heterogeneous documentation.
- PyTM automatically understands application source code.
- The four tools are semantically equivalent.
- The WordPress comparison measures precision, recall, usability or reviewer productivity.
- The review is a current 2026 inventory.
- The paper is a dedicated systematic review of model-based security testing.

## Relationship with Documentation-Driven Threat Analysis

### Base Analysis implications

A neutral Base Analysis should preserve enough typed facts to generate several tool projections:

- components and assets;
- processes, stores and actors;
- data flows and other relations;
- protocols and relationship roles;
- trust boundaries;
- technologies and deployment context;
- properties and controls;
- source provenance and uncertainty;
- version and scope.

### Methodology-plugin implications

A threat-method or tool plugin should declare:

- accepted model projection and schema version;
- catalogue identifier and version;
- rule-set identifier and version;
- required element types, properties and relations;
- candidate threat schema;
- activation evidence;
- granularity and scope;
- mitigation/control mapping;
- deduplication and overlap strategy;
- unsupported or deferred conditions.

### Candidate lifecycle

```text
candidate generated
-> review pending
-> accepted | rejected | deferred | duplicate
-> mitigation proposed
-> mitigation accepted or changed
-> evidence verified
-> rerun after model, catalogue or rule change
```

DDTA must not silently promote generated catalogue matches into accepted findings.

## Candidate thesis claims

Supported directly or conditionally:

- Automated threat-selection techniques commonly require a pre-existing typed system model.
- Threat catalogues and rule semantics are part of the method and must be versioned.
- Graph projections can support multiple selection mechanisms without becoming the canonical source of truth.
- Generated threat counts require granularity, scope and catalogue context.
- Human review remains necessary after automated candidate generation.
- Threat modelling as code can improve repeatability when its model remains synchronized.

Not supported:

- DDTA can derive a correct threat model automatically from ordinary documentation using these tools.
- A single DFD schema is sufficient for every method.
- More candidates imply better coverage.
- Any reviewed tool is complete or superior.
- Automatic rerun guarantees continuous synchronization.
- Model-based security testing is comprehensively covered by this review.

## Research gap left open

The paper starts after system interpretation. It does not explain how heterogeneous project
documentation is converted into a trustworthy typed model, how source claims retain provenance,
how uncertainty and contradictions affect rule activation, or how catalogue matches are reviewed
and maintained after documents, architecture, code and runtime evidence change.

It also leaves model-based security testing only partially covered. A dedicated recent review is
still needed for model-to-test generation, executable security properties, test oracles and
implementation-level evidence.
