## Why this source is central

The study supplies current empirical evidence about a common assumption in architectural threat
analysis: that retaining and consulting a DFD improves later validation of threats.

Its causal comparison is deliberately narrow:

```text
scenario + sequence diagram + structured threat material
versus
scenario + sequence diagram + structured threat material + DFD
```

The study therefore estimates the incremental value of the DFD when a behavioral diagram and
substantial textual information are already available. It does not estimate the absolute value of
DFDs against a no-model condition, nor does it evaluate threat elicitation.

This source is central for DDTA because it separates perceived usefulness from actual effectiveness,
challenges DFD-centric reasoning, and gives empirical weight to structured threat descriptions and
assumptions as validation evidence.

## Four reading questions

### 1. Research problem and contribution

Threat analysis frequently produces a DFD before threats are elicited, but software refinement can
make that diagram stale. The authors ask whether maintaining and using the DFD remains justified when
already identified threats must be validated.

The paper contributes:

- RQ1 on whether a DFD improves novice analysts' correctness when validating supplied threats;
- RQ2 on whether a DFD is perceived as more useful than a sequence diagram;
- one controlled experiment and one confirming experiment in different countries;
- two comparable software scenarios, Kubernetes deployment and GitHub commit/push;
- measures for actual effectiveness and perceived usefulness;
- a replication package containing experimental materials and analysis scripts;
- discussion of long-term DFD sustainability across the SDLC.

The contribution is evaluation evidence, not a new DFD notation, automated method, or documentation
extraction pipeline.

### 2. Starting artifacts and representation

All participants receive:

- a textual scenario description;
- a UML sequence diagram;
- STRIDE training and reading material;
- ten supplied candidate threats, five actual and five fabricated;
- for each threat: description, assumption, STRIDE category, and affected components;
- entry and exit questionnaires.

Only the intervention group also receives:

- a DFD;
- training that explains that DFD.

The two DFDs use comparable topology and expose:

- processes;
- data stores;
- data flows;
- external entities;
- nested trust boundaries.

The GitHub DFD represents local commit/push, scheduling and logs, GitHub protocol/controller
processing, Actions execution, and local/remote repositories. The Kubernetes DFD represents the API
server, etcd, scheduler/controller, kubelet, container engine, image repository, pod, and associated
trust boundaries.

The paper is classified as `documentation_plus_model`. Structured textual material is central, but
all system models and threat records are manually prepared by researchers. It does not demonstrate
that heterogeneous project documentation can be transformed automatically into the experimental
representations.

### 3. Traceability, change, automation and human role

The experiment uses the following evidential chain:

```text
scenario description
+ sequence diagram
+ optional DFD
+ threat description
+ threat assumption
+ STRIDE category
+ affected components
+ external technical knowledge when needed
-> actual/fabricated judgment
-> comparison with expert-curated ground truth
```

The ground truth is constructed manually:

- experienced researchers create DFDs and sequence diagrams;
- a cloud-security researcher creates an initial threat list;
- all experimenters discuss and validate the final list.

No automatic extraction, DFD generation, threat generation, assumption checking, model maintenance,
stale detection, or synchronization with code is evaluated.

The paper explicitly recognizes that DFDs can become out of sync and that maintaining architectural
assumptions is costly. It does not measure maintenance effort or define a versioned change process.
A longitudinal evaluation from design through deployment remains future work.

The replication package is declared to contain the scenarios, diagrams, threat lists, questionnaires,
reports, ground-truth rationales, information cues, technical knowledge, and analysis scripts. Package
availability does not by itself demonstrate an independently executed replication.

### 4. Findings, limitations and relationship with DDTA

#### Actual effectiveness

No significant difference was found between intervention and control for TP, TN, or TP+TN in either
experiment.

With the authors' equivalence margin `delta = 1`:

- TP was significantly equivalent in both experiments;
- TN was significantly equivalent in both experiments;
- TP+TN was not significantly equivalent in either experiment (`p = 0.18` and `p = 0.06`).

The disciplined conclusion is therefore not complete equivalence. It is:

```text
no significant performance difference;
equivalence evidence for TP and TN separately within delta = 1;
no demonstrated equivalence for the combined score.
```

#### Perceived usefulness

Participants who received both diagrams perceived the DFD as more useful than the sequence diagram:

- first experiment: `p = 0.01`;
- confirming experiment: `p = 0.002`.

This perception did not translate into a significant correctness improvement. After Bonferroni
correction, the additional correlation analysis found no significant relationship between the
reported perception/control measures and performance.

#### Structured textual evidence

Threat descriptions and assumptions were consistently rated as useful. The authors recommend clearer
and more formal documentation of these records, for example through templates.

#### Main limitations

- Student participants rather than practitioners.
- Different academic levels, countries, scenarios, and in-person/online execution.
- Every group received a sequence diagram, which may contain overlapping control- and data-flow cues.
- No no-model control group.
- Binary actual/fabricated ground truth for a nuanced security judgment.
- All fabricated threats use one contradiction pattern.
- Self-reported perception measures.
- Researcher-curated ground truth.
- Equivalence conclusions depend on the chosen `delta = 1`.
- Threat difficulty was manually coded and did not yield strong performance evidence.
- A likely internal reporting inconsistency: total population is 98, while one validity paragraph
  refers to `67/100`; the paper does not explain the discrepancy.

## Core definitions

### Threat validation

Judging whether a supplied candidate security threat is valid under the scenario, assumptions, model
cues, and relevant technical knowledge.

### Actual threat

A candidate threat whose description remains plausible under the supplied assumptions and system
information according to the expert-curated ground truth.

### Fabricated threat

A false threat claim intentionally created in this study by making its assumption contradict a
capability required by the threat description.

### Actual effectiveness

The number of correctly classified actual threats (TP) and correctly classified fabricated threats
(TN), also reported as a combined TP+TN score.

### Perceived usefulness

Participants' Likert-scale judgment of how useful the supplied experimental artifacts were during
validation.

### Information cue

A piece of information needed for validation, located in an assumption, scenario description,
graphical model, or external technical knowledge.

## Starting artifacts and minimum input

Minimum real input for the reported task:

- a bounded and understandable software scenario;
- a sequence diagram;
- a supplied list of candidate threats;
- explicit threat descriptions and assumptions;
- STRIDE categories and affected components;
- sufficient technical/domain knowledge;
- a ground truth for evaluation;
- optionally, a DFD as the intervention.

The paper does not define minimum quality requirements for ordinary project documentation and does
not test missing, contradictory, stale, or heterogeneous source documents.

## Representation and model

The study combines multiple views rather than treating the DFD as complete:

1. textual scenario description;
2. UML sequence diagram for ordered interactions;
3. DFD for processes, stores, flows, external entities, and trust boundaries;
4. structured threat record;
5. expert ground-truth rationale;
6. external technical knowledge for hard validation tasks.

The two scenario DFDs were deliberately matched in graph topology. This design controls diagram size
but does not establish semantic equivalence between a DFD and sequence diagram.

## Procedure

1. Recruit students from the target courses and obtain consent.
2. Collect an entry questionnaire about relevant background.
3. Randomly allocate intervention and control groups.
4. Provide two hours of training and scenario material.
5. Provide the sequence diagram to every participant and the DFD only to intervention participants.
6. Ask each participant to classify ten threats as actual or fabricated.
7. Collect exit-questionnaire perceptions and control measures.
8. Compare classifications against expert-curated ground truth.
9. Count TP, TN, and TP+TN.
10. Test differences and equivalence.
11. Compare perceived usefulness of diagrams.
12. Perform additional corrected correlation analysis.

## Traceability, change, automation and human role

### Traceability present

Each candidate threat connects:

```text
description
-> assumption
-> STRIDE category
-> affected components
-> information cue / technical knowledge
-> ground-truth rationale
-> participant judgment
```

The paper and replication package provide a basis for research traceability. They do not define
assertion-level provenance from the scenario back to original engineering documents.

### Change and evolution

The introduction recognizes DFD drift during design refinement. The study does not manipulate
document or design changes and does not measure update effort, stale detection, or change impact.

### Automation

No automated documentation ingestion, model generation, threat validation, or lifecycle maintenance
is evaluated. Statistical analysis scripts are reported in the replication package; that is research
analysis automation, not threat-analysis automation.

### Human responsibility

Researchers construct and validate the experimental objects and ground truth. Participants use
supplied evidence and their own technical knowledge to make binary judgments.

## Evaluation evidence

### Participants and groups

- Total: 98.
- First experiment: 48.
- Confirming experiment: 50.
- Intervention groups: 50 total.
- Control groups: 48 total.
- Population: third-year BSc and first-year MSc computer-science students with limited security-analysis experience.

### Scenarios

- Kubernetes pod deployment.
- GitHub commit and push.
- Comparable DFD topology and sequence structure.

### Actual effectiveness means

First experiment:

```text
Group A: TP 3.1, TN 3.1, TP+TN 6.3
Group B: TP 2.9, TN 2.9, TP+TN 5.7
```

Confirming experiment:

```text
Group A: TP 4.4, TN 2.4, TP+TN 6.8
Group B: TP 4.3, TN 2.7, TP+TN 7.0
```

No test of difference was significant.

### Perception-performance separation

DFD perception was significantly higher than sequence-diagram perception in intervention groups, but
the DFD did not significantly improve validation correctness. This is a direct empirical warning
against using perceived usefulness as a proxy for actual effectiveness.

### Results not obtained

- No evidence about expert practitioners.
- No evidence about threat elicitation.
- No no-model comparison.
- No longitudinal model-maintenance evidence.
- No maintenance-cost measure.
- No completeness or recall measure for discovering threats.
- No evidence that DFD and sequence diagram are semantically equivalent.
- No strong evidence that manually coded difficulty predicts performance.

## Documentation-first classification

### Classification

`documentation_plus_model`

The task can occur before code exists, but it depends on manually prepared system diagrams, structured
threats, assumptions, and a ground truth. Raw heterogeneous documentation is not shown to be sufficient.

### Nine documentation-first fields

1. Input and quality: structured scenario, diagrams, threat records, training, and domain knowledge;
   ordinary-document quality is not specified.
2. Compatibility: `documentation_plus_model`.
3. Intermediate representation: textual scenario + sequence diagram + optional DFD + threat record.
4. Procedure: trained novice classification against expert ground truth.
5. Output: binary validity judgments, performance metrics, and perception scores.
6. Provenance, uncertainty, review: ground-truth rationale exists; assertion-level source provenance,
   confidence, and review state are not modeled.
7. Evolution/change: DFD drift is recognized; no update mechanism is evaluated.
8. Evaluation/evidence: controlled and confirming academic experiments with 98 students.
9. Thesis use: evidence on incremental DFD value, perception-performance divergence, and assumption
   documentation; not evidence that DFDs are generally ineffective.

## Directly supported

- Under the tested conditions, an extra DFD did not significantly improve novice threat-validation correctness.
- TP and TN performance were equivalent within `delta = 1`; combined-score equivalence was not shown.
- Participants perceived the DFD as more useful than the sequence diagram when both were supplied.
- Perceived usefulness did not imply a measurable correctness gain.
- Threat descriptions and assumptions were important validation materials.
- DFD information cues include presence or absence of flows, processes, stores, and trust boundaries.
- Some threat judgments require technical knowledge not contained in either text or diagrams.
- Longitudinal DFD utility from design to deployment remains open.

## Not supported

- DFDs are useless in general.
- DFDs do not help threat elicitation.
- DFDs can be safely discarded after elicitation.
- Text alone is sufficient for threat validation.
- Experts would obtain the same results.
- Sequence diagrams and DFDs are semantically equivalent.
- The DFD has no value for model-code compliance, testing, or other SDLC phases.
- The reported ground truth is complete.
- The experiment validates automatic model generation or continuous synchronization.
- The study proves that a neutral DDTA Base Analysis should exclude a DFD projection.

## Eight DDTA evidence questions

1. Documents sufficient without code: structured scenario, sequence diagram, candidate threats,
   assumptions, categories, and affected components; raw project documents are not evaluated.
2. Neutral intermediate representation: not directly answered; the combined views suggest a typed
   context with processes, stores, flows, interactions, boundaries, assumptions, and threat records.
3. Extracted versus inferred: not answered.
4. Method as overlay: STRIDE categories and threat validation can operate over multiple Base Analysis
   projections rather than a DFD-only model.
5. Provenance, confidence, review: partial ground-truth rationale; no governed provenance/confidence states.
6. Documentation change: DFD drift is recognized but not evaluated.
7. Later code evidence: referenced related work only; not tested in this experiment.
8. Measurement: actual correctness, perception, difference/equivalence tests, and limited task-difficulty coding;
   no completeness, traceability, maintenance-cost, or expert-review metrics.

## Temporal validity

- Contribution type: current controlled empirical evaluation.
- Time sensitivity: low for the observed experiment; replication is required for broader populations and contexts.
- Temporal status: current evidence published in 2025.
- Evidence window: novice participants, two academic cohorts, two scenarios, sequence diagram supplied to all.
- Still applicable: perception-performance separation, importance of assumptions, and careful interpretation of
  incremental model value.
- Potentially unstable: replication-package location and availability.
- Contemporary corroboration required: experts, no-model controls, alternative diagrams, harder tasks,
  longitudinal model use, maintenance cost, and human-factor analysis.
- Permitted thesis use: challenge DFD-centric assumptions and motivate multi-view, evidence-based evaluation.
- Prohibited overclaim: general DFD ineffectiveness or semantic redundancy.

## Relationship with Documentation-Driven Threat Analysis

### Base Analysis implications

A neutral Base Analysis should preserve facts needed by several views:

- processes and components;
- data stores and data flows;
- ordered interactions;
- actors and external entities;
- trust boundaries;
- requirements and system assumptions;
- threat descriptions and affected elements;
- external knowledge dependencies;
- provenance and review state.

The DFD should be one projection of this model, not necessarily the canonical storage model.

### Overlay implications

A STRIDE or validation overlay can:

- select relevant Base Analysis elements;
- generate or attach candidate threats;
- record the assumption under which each threat is plausible;
- indicate information cues used for validation;
- distinguish accepted, rejected, and unresolved threats;
- record analyst rationale and required external knowledge;
- measure correctness and review disagreement;
- invalidate judgments when assumptions or source evidence change.

### Provenance, uncertainty and review controls

DDTA must add controls absent from the study:

- assertion-level source provenance;
- extracted/inferred/analyst-supplied classification;
- confidence and unresolved contradiction handling;
- independent review and reviewer agreement;
- versioned threat assumptions and attacker profiles;
- reasoned acceptance/rejection rather than only binary labels;
- model-projection consistency;
- stale detection and change-impact links;
- evidence that a visualization improves an intended outcome, not only perception.

## Candidate thesis claims

Supported directly or conditionally:

- Model usefulness must be evaluated against a specified task and baseline.
- Perceived usefulness is not a valid proxy for actual correctness.
- Threat assumptions and descriptions are first-class validation evidence.
- A DFD can be represented as a projection over a richer neutral model.
- Additional diagrams may not improve correctness when overlapping information is already supplied.
- Equivalence claims must preserve their margin and outcome-specific scope.

Not supported:

- DFDs should be removed from DDTA.
- DFDs do not contribute to STRIDE elicitation.
- Sequence diagrams replace all security-relevant DFD semantics.
- Novice student results generalize to experts.
- A combined textual and model representation guarantees correct threat validation.
- The experiment measures documentation-to-model derivation.

## Research gap left open

The study begins with expertly prepared diagrams, structured candidate threats, and a curated ground
truth. It does not explain how heterogeneous, versioned engineering documentation becomes those
trustworthy artifacts, how information cues retain assertion-level provenance, how uncertainty and
multiple attacker profiles are represented, or how validation judgments are revised when documents,
assumptions, architecture, code, and runtime evidence change.

It also leaves open whether a maintained multi-view Base Analysis improves longitudinal outcomes enough
to justify its creation and synchronization cost.
