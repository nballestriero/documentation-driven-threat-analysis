## Why this source is central

This full-text historical edition gives the exact conceptual model behind architecture description, views, viewpoints, model kinds, correspondences, decisions and rationale. It is particularly valuable because it both supports and falsifies parts of the BA0-R working hypothesis: it sharply separates architecture from architecture description and view from viewpoint, but it explicitly supports both **synthetic** and **projective** approaches to building views. Therefore it does not establish that every architecture view must be a projection of one underlying canonical repository.

## Four reading questions

### 1. Research problem and contribution

The standard specifies how architecture descriptions are organized and expressed, including requirements for architecture descriptions, architecture viewpoints, architecture frameworks and architecture description languages. Its conceptual foundation treats architecture as the fundamental concepts or properties of a system in its environment, embodied in elements, relationships and design/evolution principles, while an architecture description is the work product used to express an architecture.

The standard deliberately does **not** define the nature of a system, prescribe a modeling notation, prescribe an architecting method, or require one recording medium. This is crucial for DDTA: ISO 42010 is architecture-description governance prior art, not a ready-made system ontology or BAE kernel.

### 2. Starting artifacts and generated representations

The conceptual model distinguishes:

```text
System-of-Interest
    -> exhibits Architecture
Architecture Description
    -> expresses Architecture
    -> identifies Stakeholders / Concerns
    -> contains Views / Models / Correspondences / Rationale
Viewpoint
    -> frames Concerns
    -> governs a View
    -> specifies one or more Model Kinds
View
    -> is composed of one or more Architecture Models
Architecture Model
    -> is governed by a Model Kind
```

A model kind defines modeling conventions. Annex B explicitly says a model-kind metamodel can describe **entities, attributes, relationships and constraints**. That is a strong external confirmation of the BA0-R extraction lens, but not a DDTA class prescription.

The standard also provides decomposition/allocation examples in which system items/elements and their interfaces are identified and requirements are allocated to them. RM-ODP examples show that roles, information schemas, interfaces, interactions and communication channels can belong to different viewpoints/languages rather than one universal architecture ontology.

### 3. Traceability, change, automation and human role

The standard introduces **correspondences** as explicit relations among architecture-description elements and allows correspondence rules to govern those relations. Correspondences can express consistency, traceability, composition, refinement, dependency, constraint, model transformation and related cross-model relations. They may be n-ary, may span models/views/architecture descriptions, and may be extended to relations between architecture-description elements and other work products such as requirements specifications.

Architecture decisions and rationale are also explicit prior art. The standard recommends recording key decisions with unique identity, affected AD elements, concerns, owner, rationale, constraints/assumptions, alternatives, consequences, timestamps and source citations. This strongly overlaps with DDTA's existing Decision/provenance concerns but does not falsify the closed DDTA documentation hierarchy because ISO 42010 addresses architecture-description work products rather than DDTA's ownership/decomposition semantics.

Architecture descriptions may aggregate information from several life-cycle work products and may serve as input to automated simulation, generation and analysis tools. Generic model-based analysis therefore cannot be claimed as DDTA novelty.

### 4. Findings, limitations and relationship with DDTA

#### Direct support

- architecture and architecture description are distinct concepts;
- view and viewpoint are distinct: viewpoint provides conventions, view applies them to a system-of-interest;
- a view contains one or more architecture models, and one architecture model may belong to more than one view;
- shared models can reduce repetition and inconsistency across views;
- correspondences provide explicit cross-model/view relation semantics and rule-governed consistency/traceability;
- architecture decisions and rationale are established prior art;
- model kinds may be specified through metamodels with entities, attributes, relationships and constraints;
- architecture descriptions can support analysis across the life cycle without prescribing one method or notation.

#### Important falsification of an earlier BA0-R formulation

The standard describes two common ways to construct views:

```text
synthetic approach
    construct views separately
    -> integrate through correspondences

projective approach
    derive views by extraction from an underlying repository
```

It is explicitly usable with either. Therefore the earlier DDTA wording:

```text
canonical model -> projection -> view
```

is **not** a general result established by ISO 42010. It remains a plausible DDTA design candidate because it may simplify consistency, provenance and regeneration, but BA0/BA4 must justify that choice rather than present it as the only architecture-description semantics.

#### Terminology pressure on BA4

Under the 2011 standard, an architecture view addresses concerns and covers the whole system from its governing viewpoint, while individual architecture models may selectively present portions of the system. Therefore a small generated diagram or filtered graph should not automatically be called an `ArchitectureView` if DDTA wants ISO-aligned terminology. `Projection`, `rendering` or `model` may be more precise for partial presentations.

#### System-ontology boundary

ISO 42010 explicitly takes no position on what constitutes a system. It therefore cannot select `Actor`, `Asset`, `Interaction`, `Channel`, `State`, `Store` or any other DDTA BAE root. It strengthens the distinction between **architecture-description ontology** and **system-model ontology**.

## Chapter regression

No Chapter 3 or Chapter 4 reopen trigger is produced.

- Chapter 3: the standard establishes architecture-description/view/correspondence/decision prior art, but does not establish the DDTA end-to-end documentation -> security analysis -> reviewed finding -> governed change -> re-analysis loop.
- Chapter 4: architecture decisions/rationale overlap conceptually with DDTA Decision, but no concrete contradiction is shown against the closed DDTA MR/Decision/Requirement hierarchy.

The main downstream correction belongs to BA0/BA4: DDTA must justify a canonical-projective representation if selected, and must use `view` terminology carefully.
