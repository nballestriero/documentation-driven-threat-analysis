## Four reading questions

### 1. Research problem and contribution

The paper addresses the difficulty of identifying and framing software problems. It uses process models as explicit contextual input and maps them toward Problem Frames so that business/process context can inform software requirements more systematically.

### 2. Starting artifacts and system representation

The starting artifact is a process model (role-activity diagrams in the reported work) containing contextual knowledge. The paper treats framing as difficult rather than assuming that every real problem naturally fits one of a few predefined frames.

### 3. Traceability, change, automation and human role

The work is analyst-led/action-research in an industrial project. Indexed text indicates that guidelines evolved during the project. It does not report an automatic framing engine or DDTA-style provenance/authority states.

### 4. Findings, limitations and relationship with DDTA / overlay

A key pressure-test result in the accessible text is that the software problem did not always map easily to Jackson's small set of frames; the authors still found problem diagrams useful. Generality is limited by one industrial case. This is important negative evidence against treating a small catalogue as complete.

## Findings

- Framing is itself a difficult analytical task.
- Real industrial problems may not map cleanly to a small fixed frame catalogue.
- Process models can provide explicit context for subsequent problem analysis.
