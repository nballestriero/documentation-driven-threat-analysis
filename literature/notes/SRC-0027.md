## Why this source is central

The paper provides an explicit assurance layer for security requirements engineering. It links
business and functional goals, system context, assets and harms, security goals, security
requirements represented as constraints, formal proofs, structured informal arguments, trust
assumptions, rebuttals and mitigations.

It is important for DDTA because it separates three questions that are often conflated:

1. what a security requirement is;
2. which assumptions make it credible;
3. whether the modeled system can satisfy it.

The framework does not extract a context or behavior specification directly from heterogeneous
documentation. Stage 1 requires a system-context representation but leaves open how it is
obtained. Assurance is therefore downstream of documentation interpretation and Base Analysis.

## Four reading questions

### 1. Research problem and contribution

The paper asks how to determine adequate security requirements for a complete system that includes
software, people, equipment and surrounding domains. Adequacy requires:

- definition: a coherent operational meaning;
- assumptions: explicit treatment of trust assumptions;
- satisfaction: evidence that goals and requirements can be met.

The journal paper unifies earlier work on artifacts, threat descriptions, trust assumptions and
satisfaction arguments and reports application of the integrated framework in CRISTAL UK.

### 2. Starting artifacts and representation

The method is pre-code but requires or creates structured artifacts:

- application business and quality goals;
- functional requirements;
- system context and boundary;
- domains and interconnections;
- shared phenomena;
- behavior descriptions;
- assets and harms;
- management control principles and policies;
- security goals;
- trust assumptions.

Jackson-style problem diagrams describe domains, interconnections, shared phenomena and
requirements. The framework does not require a specific problem-frame class. It does not analyze
raw documentation directly.

### 3. Traceability, change, automation and human role

The traceable chain is:

```text
business and functional goals
-> system context and functional requirements
-> assets, harms and security goals
-> security constraints
-> outer satisfaction argument
-> inner arguments and trust assumptions
-> rebuttals
-> mitigation or accepted residual assumption
-> secondary functions, goals and requirements
-> revised context and new iteration
```

Dependencies run downward through derivation and upward through feasibility. Failure to justify a
lower-level artifact can force revision of its ancestors.

Human analysts and stakeholders still choose boundaries, assets, harms, applicable policies,
logic, assumptions, rebuttals, mitigations and acceptable residual risk. The framework does not
define source-document provenance, versioned impact analysis or automated argument maintenance.

### 4. Findings, limitations and relationship with DDTA

A failed satisfaction argument is useful evidence. It may reveal:

- an infeasible security requirement;
- an underspecified context;
- an unjustified behavior premise;
- an implicit trust assumption;
- a rebuttal requiring mitigation;
- a need for new functions, assets, goals or requirements.

The CRISTAL UK application produced security requirements, rebuttals and mitigations not
previously considered. It also showed practitioner difficulty with formal outer arguments,
preference for less expressive graphical arguments, lack of a complete rebuttal-discovery recipe,
need for nonexpert challenge and need for stronger tool support.

The evidence is one industrial research application plus examples, not a controlled experiment or
comparative benchmark.

## Core definitions

### System

The system includes software, people, equipment, physical and operating environments and existing
systems included in the chosen boundary.

### Asset, harm and threat description

An asset is a tangible or intangible resource of value. A threat description has the form:

```text
action + asset + harm
```

Security goals are derived by preventing or avoiding harmful actions on assets.

### Security requirement

A security requirement is a prescriptive constraint on a specific functional requirement. It
operationalizes one or more security goals and should be precise enough for a designer or
architect. It is not merely a quality aspiration, mechanism, policy or attacker scenario.

### Primary and secondary artifacts

Primary security goals and requirements are derived directly from business goals, functions,
assets and harms. Secondary artifacts are added when a primary requirement is infeasible or its
satisfaction argument is unacceptable. They may cover and replace the primary artifact
operationally, but do not delete it.

## Four-stage framework

### Stage 1 - Identify functional requirements

Produce or revise business goals, quality goals, system context and functional requirements. The
only mandatory framework output is a representation of system context; its derivation method is
outside the framework.

### Stage 2 - Identify security goals

1. Identify candidate assets.
2. Select applicable management principles and policies.
3. Perform or reuse harm analysis.
4. Build threat descriptions.
5. Derive and validate security goals against business goals.
6. Resolve inconsistent goals.

### Stage 3 - Identify security requirements

1. Determine which assets participate in each function.
2. Determine which security goals apply.
3. Constrain the relevant functional requirements.
4. Validate that the constraints satisfy the security goals.

### Stage 4 - Construct satisfaction arguments

1. Annotate the context with shared phenomena.
2. Specify relevant domain behavior.
3. Construct the formal outer argument.
4. Identify premises and assumptions.
5. Construct structured inner arguments.
6. Discover rebuttals and unsupported trust assumptions.
7. Mitigate, justify, weaken or reject problematic claims.
8. Revise context, goals and requirements when needed.

## Satisfaction-argument model

### Outer argument

The outer argument establishes:

```text
domain behavior premises |- security requirement
```

Its conclusion is conditional on correct and complete context and behavior, and on implementation
introducing no conflicting behavior. The paper explicitly states that this does not prove that the
implemented system will be secure.

### Inner argument

The inner argument supports and challenges the premises of the outer argument. Its typed elements
include claim, grounds, warrant, backing, modal qualifier, rebuttal, subargument and trust
assumption. Recursive argumentation terminates at unsupported grounds classified as trust
assumptions.

### Trust assumption

A trust assumption is an unsupported claim about behavior or properties of the world. DDTA should
add identity, scope, evidence, confidence, reviewer, rebuttals and change monitoring.

## Iteration and evolution

Insufficient evidence can trigger concurrent requirements-and-design iteration. A mitigation may
introduce new domains, phenomena, functions, assets, goals, requirements, assumptions and
rebuttals. The paper supports semantic change propagation but does not define versioned snapshots,
stale states or executable impact rules.

## CRISTAL UK / NATS application

The case evaluated whether ADS-B position reports could be used as a primary position source.
Initial artifacts included:

- one functional goal and one functional requirement;
- direct and indirect assets;
- eight threat descriptions;
- two security goals for correct and timely positions;
- two security constraints for accuracy and timeliness;
- an outer proof over the modeled behavior;
- twelve initial rebuttals.

Intentional false-position transmission was treated as unacceptable. Multilateration was added as
a mitigation, which generated new rebuttals concerning transmitter identity, virtual
transmitters and clock synchronization. The case demonstrates recursive mitigation analysis.

## Practitioner lessons

- More expressive logic can expose hidden assumptions but increases reasoning complexity.
- Some practitioners wanted to skip the outer argument because it proves only conditional
  satisfaction.
- Textual arguments were expressive but difficult at scale; graphics were easier but lossy.
- No complete recipe was available for finding grounds, warrants and rebuttals.
- Domain experts could normalize hidden assumptions; nonexperts helped challenge them.
- Interacting rebuttals and mitigations require coordinated analysis.
- Security analysis can expand context to unexpected domains and needs scope control.

## Documentation-first classification

### Classification

`documentation_plus_problem_context_behavior_model_required_or_created`

### Directly supported

- Analysis can begin before code exists.
- Early core artifacts can be documents, models or prototypes.
- The context can include people, equipment and environment.
- Security requirements can be linked to exact functions.
- Trust assumptions and rebuttals can be explicit.
- Failed arguments can diagnose missing context.
- Iteration can add design detail and new requirements.

### Not supported

- Direct extraction of context from heterogeneous documentation.
- Automatic identification of assets, harms or domains.
- Complete or objective threat discovery.
- Proof that the implemented system will be secure.
- Proof that all relevant behaviors were included.
- Exact source-document-to-claim provenance.
- Quantitative validation of improved security outcomes.
- A complete algorithm for rebuttal discovery.
- A global stopping criterion.

## Temporal validity

- Contribution type: foundational security-requirements assurance framework.
- Time sensitivity: low to medium for concepts; high for tools and maturity.
- Temporal status: foundational framework with a single industrial application.
- Still applicable: context dependence, constraints on functions, explicit assumptions,
  conditional assurance, rebuttal-driven iteration and artifact dependencies.
- Potentially obsolete: historical tools and notation choices.
- Contemporary corroboration required: continuous assurance, machine-readable argument graphs,
  automated change impact, current usability studies and integration with code/runtime evidence.
- Permitted thesis use: establish the distinction between definition, assumptions and
  satisfaction and demonstrate pre-code assurance over structured context and behavior models.

## Relationship with Documentation-Driven Threat Analysis

### Research gap left open

The framework starts after a problem context and functional behavior have been represented. It
does not define how heterogeneous, versioned documentation becomes that context, how every domain
or phenomenon remains linked to source assertions, or how argument validity is incrementally
re-evaluated after documentation, code or runtime evidence changes.

### Overlay and assurance implications

- Expose problem-context, behavior, asset and harm views from Base Analysis.
- Keep Base Analysis facts distinct from security constraints and assurance claims.
- Link every security constraint to the function it constrains.
- Separate goal-to-requirement validation from system-to-requirement satisfaction.
- Represent outer premises, conclusion, logic and proof status.
- Represent inner claims, grounds, warrants, backing, qualifiers and rebuttals.
- Treat unsupported leaves as explicit trust assumptions.
- Attach source provenance and extracted/inferred status to every premise.
- Preserve primary and secondary artifacts through non-destructive cover/replace relations.
- Preserve rejected mitigations and alternatives.
- Add incomplete-context and unprovable-requirement diagnostics.
- Re-run affected argument fragments after Base Analysis changes.
- Use later code, tests and runtime evidence to confirm or contradict assumptions.
- Measure effort, rebuttal yield, accepted mitigation yield and requirement quality.

## Candidate thesis claims

The source supports claims that security requirements should be context-specific constraints on
functional requirements, that trust assumptions should be explicit and that formal-plus-informal
arguments can diagnose missing information and system-level vulnerabilities before implementation.

It cannot support claims that the implemented system is secure, every relevant threat was found,
heterogeneous documentation is automatically sufficient, argument construction is automated or
the framework is empirically superior.
