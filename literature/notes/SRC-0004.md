## Why this source is central

This paper presents a goal-oriented and partly formal method for deriving application-specific
security requirements before implementation. It constructs two concurrent models:

- a primal model of the system-to-be and its environment;
- an intentional anti-model describing attackers, anti-goals, capabilities, vulnerabilities and
  malicious operationalizations.

The method is directly relevant to DDTA because it shows how threats and countermeasures can be
derived from a structured requirements model while retaining goal, agent and object relations.
It does not solve the preceding transformation from heterogeneous documentation to that
structured primal model, nor does it preserve traceability to exact source assertions.

## Four reading questions

### 1. Research problem and contribution

The paper addresses the lack of systematic application-layer security requirements engineering.
It proposes six meta-requirements for a security RE technique:

- early deployment on declarative assertions from interviews and documents;
- incremental reasoning over partial models;
- explicit representation of alternatives;
- formal analysis where high assurance is needed;
- security-by-construction;
- separation of security and other requirements for interaction analysis.

The contribution extends the KAOS obstacle framework with malicious obstacles called anti-goals.
Threat trees are refined until terminal nodes are:

- anti-requirements realizable by an attacker; or
- software vulnerabilities observable or exploitable by that attacker.

Countermeasure operators then generate candidate security goals, which are refined into software
requirements and environmental expectations.

### 2. Starting artifacts and system representation

The method can start before code, state machines or complete design models. It nevertheless
requires, or incrementally constructs, a structured primal model containing:

- goals and security goals;
- agents in the software and environment;
- objects and sensitive information;
- operations;
- domain properties;
- requirements assigned to software agents;
- expectations assigned to environmental agents;
- assumptions and non-functional goals.

Security goal patterns for confidentiality, privacy, integrity, availability, authentication and
non-repudiation are instantiated against sensitive objects in the object model. Generic
predicates such as authorization or control must be specialized with application-specific
definitions.

The method therefore accepts early documentary assertions, but it does not operate directly on
raw documentation. The assertions must be interpreted into goal, object, agent and domain models.

### 3. Traceability, change, automation and human role

The approach creates typed model relations:

```text
security goal
-> negated initial anti-goal
-> attacker and higher-level anti-goals
-> AND/OR anti-goal refinements
-> anti-requirement or vulnerability
-> alternative countermeasure
-> selected security goal
-> requirement or expectation
```

Formal regression through domain properties and primal goals can derive anti-goal preconditions.
Refinement and obstruction patterns provide a cheaper structured alternative. When anti-goals
are formalized in temporal logic, bounded SAT solvers can generate attack scenarios.

Automation is therefore possible only after a sufficiently formal model exists. Human analysts
still have to:

- identify sensitive objects;
- instantiate security patterns;
- specialize domain predicates;
- elicit attacker classes and attacker motives;
- supply domain properties;
- assess likelihood and criticality;
- select among countermeasures using other quality goals.

The model/anti-model cycle is explicitly iterative. New security goals may require new refinement
and a new anti-model cycle. Runtime anti-goal monitoring is suggested for deferred resolutions,
but versioning and change-impact rules are not defined.

### 4. Findings, limitations and relationship with DDTA

The paper demonstrates a web-banking derivation and reports three additional anti-model case
studies. The underlying goal-oriented method had broader industrial use, but the security
anti-model transposition had only four reported cases. There is no controlled comparison, common
benchmark, precision/recall evaluation or analyst-effort measurement.

Compared with misuse cases, the method offers:

- stronger model semantics;
- formal derivation and local proof obligations;
- explicit attacker capabilities and software vulnerabilities;
- alternative countermeasure operators.

Its costs and limits include:

- substantial goal, object and domain modeling effort;
- dependence on analyst elicitation for attackers, motives and domain properties;
- no guaranteed global termination of the requirement/anti-requirement/countermeasure cycle;
- incomplete empirical validation of the anti-model extension;
- no source-document provenance;
- no current evidence on tool usability or scalability.

For DDTA, intentional anti-models are best represented as a goal-oriented methodology overlay
applied to goal, agent, object and operation views derived from Base Analysis.

## Research method and evidence

This is a constructive method paper illustrated by a detailed case study and supported by three
additional reported applications.

The paper distinguishes:

- prior industrial validation of the general KAOS goal-oriented method across more than 25
  projects;
- limited validation of the anti-model extension in four case studies.

The four anti-model cases include:

1. the web-banking case presented in the paper;
2. a Belgian smartcard payment system;
3. a web-based CD order-tracking system;
4. an e-commerce system with an independent payment-processing agent.

The evidence supports feasibility and expressive power. It does not establish superiority,
scalability, reproducibility or comparative effectiveness.

## Primal-model concepts

### Goals and refinement

Goals are prescriptive statements organized in AND/OR refinement hierarchies. Refinement ends
when terminal goals are realizable by individual agents.

### Requirements and expectations

- A terminal goal assigned to a software-to-be agent is a requirement.
- A terminal goal assigned to an environmental agent is an expectation.

This distinction is important for DDTA because a security outcome may require software behavior,
environmental policy or both.

### Agents and objects

Agents include humans, devices, legacy software and software-to-be components. Objects are passive
or active domain entities referenced by goals and operations. Agent interfaces are expressed
through what agents monitor and control.

### Domain properties

Domain properties describe the environment. They are used during formal regression to derive
conditions under which goals can be obstructed.

## Security concepts

- Security goals specialize confidentiality, privacy, integrity, availability, authentication and
  non-repudiation.
- Attackers are malicious environmental agents.
- Threats are intentional obstacles to security goals.
- Assets are active or passive objects.
- Anti-goals are attacker-owned goals, including malicious obstacles.
- Anti-requirements are terminal anti-goals realizable by attacker agents.
- Vulnerabilities are terminal anti-goals realizable by software attackee agents.
- Attacker capabilities operationalize anti-requirements.

These concepts form an intentional explanation of why, how and by whom a security goal may be
violated.

## Six-step anti-model building method

### Step 1 - Generate initial anti-goals

Negate relevant security goal patterns instantiated against sensitive objects.

### Step 2 - Elicit attackers

Ask who can benefit from each anti-goal. Attacker taxonomies may assist, but the result remains
application-specific.

### Step 3 - Elicit higher-level anti-goals

Ask why an attacker class would want the anti-goal. Repeating this question produces attacker
rationales and alternative threat branches.

### Step 4 - Refine the anti-goal graph

AND/OR-refine anti-goals until terminal goals are realizable by attackers or software attackees.

- attacker-realizable leaves become anti-requirements;
- attackee-realizable leaves become vulnerabilities.

Refinement can be informal through HOW/WHY questions or formal through regression and patterns.

### Step 5 - Derive anti-object and anti-agent models

Derive the attacker-controlled anti-machine, anti-environment, referenced objects and
monitor/control interfaces.

### Step 6 - Operationalize attacker capabilities

Turn anti-requirements into potential operations such as searching, eavesdropping, deciphering or
spoofing.

## Countermeasure generation

The paper proposes general obstacle-resolution operators:

- goal substitution;
- agent substitution;
- goal weakening;
- goal restoration;
- anti-goal mitigation;
- anti-goal prevention.

It adds security-specific operators:

- protect vulnerability;
- defuse threat;
- avoid vulnerability.

Alternative resolutions are selected according to severity, likelihood and other non-functional
goals. The chosen resolution becomes a new security goal that must be refined to requirements and
expectations.

## Documentation-first classification

### Classification

`documentation_plus_goal_object_domain_model_required_or_created`

### Directly supported

- The method can begin from stakeholder interviews and documents.
- It works before source code and complete operational models.
- It supports partial and incrementally constructed models.
- Security patterns can generate application-specific goal candidates.
- Anti-goal refinement links threats to vulnerabilities, attacker capabilities and
  countermeasures.
- Formal techniques can provide local derivation and refinement evidence.

### Not supported

- Direct analysis of heterogeneous raw documentation without model construction.
- Automatic identification of sensitive objects, attackers, motives or domain properties.
- A methodology-neutral Base Analysis.
- Exact document-to-model provenance.
- A global completion or termination guarantee.
- Comparative empirical evidence that the method improves threat-model quality.

## Main findings

- Goal negation provides an explicit starting point for threat analysis.
- Attacker motives can guide threat refinement beyond immediate attack steps.
- The distinction between anti-requirements and vulnerabilities separates attacker capability
  from attackee weakness.
- Formal regression can derive threat preconditions from domain properties and primal goals.
- Some refinements can carry local proof of completeness.
- Countermeasure operators make alternatives explicit.
- Requirements and environmental expectations are distinct outcomes.
- The method remains dependent on analyst modeling and selection decisions.
- Formal automation is downstream of structured model construction, not a substitute for it.

## Limitations

### Stated or acknowledged by the author

- Only four anti-model case studies had been conducted.
- Termination of the requirement/anti-requirement/countermeasure cycle remained open.
- Richer threat and countermeasure pattern catalogues were needed.
- Trust and trustworthy-agent modeling remained open.
- Probabilistic treatment of partial satisfaction and anti-goal likelihood remained open.
- Criticality among vulnerabilities required further differentiation.

### Additional limitations for DDTA comparison

- The initial primal model has a high documentation-interpretation and modeling cost.
- Formal derivation depends on the correctness and completeness of domain properties.
- Local proof-complete refinements do not imply global threat completeness.
- The paper does not distinguish extracted facts from analyst assumptions or hypotheses.
- Source-document provenance is absent.
- No versioned snapshot, stale-analysis or incremental change-impact contract is defined.
- Tool references and usability evidence are historically dated.
- Evaluation does not measure analyst effort, review yield or downstream requirement quality.

## Temporal validity

- Contribution type: foundational formal requirements-engineering method.
- Time sensitivity: medium for method concepts; high for tools and empirical maturity.
- Temporal status: foundational method with limited anti-model validation.
- Still applicable: model/anti-model duality, goal-anchored threat analysis, attacker rationale,
  typed leaves, formal regression, alternative countermeasures and software/environment
  responsibility.
- Potentially obsolete: historical tools, specific logic/toolchain assumptions and maturity claims
  from 2004.
- Contemporary corroboration required: current GORE security tools, recent empirical studies,
  automated document-to-model extraction, continuous threat analysis and human-review metrics.
- Permitted thesis use: demonstrate a pre-code, model-based and partly formal path from security
  goals to threats and security requirements. Do not use it as proof of raw-document sufficiency,
  global completeness, automation or comparative superiority.

## Relationship with Documentation-Driven Threat Analysis

### Directly supported propositions

- Early security analysis can start from declarative assertions in interviews and documents.
- Partial models can be analyzed incrementally.
- Security goals, attacker goals, vulnerabilities and countermeasures should be distinct.
- Software requirements and environmental expectations should be distinguished.
- Threat derivation may use explicit domain properties and formal proof obligations.
- Alternative threat refinements and countermeasures should be preserved.
- Human selection remains necessary even with formal derivation support.

### Tensions

- Early deployment still depends on substantial structured modeling.
- Formal assurance increases confidence in a derivation relative to a model, not in the
  completeness of the source documentation or model.
- Goal anchoring gives a clear starting point but can omit threats outside the selected goals.
- Attacker-intent modeling explains rationale but may depend on speculative assumptions.
- Pattern catalogues improve repeatability but can constrain discovery to known classes.
- Iterative construction supports evolution but lacks an explicit termination rule.

### Research gap left open

The method does not govern how heterogeneous, versioned documentation is transformed into a
neutral and reviewable model of goals, agents, objects, operations and domain properties. It also
does not preserve assertion-level provenance, uncertainty or explicit change-impact evidence.

### Overlay-method implications

- Expose goal, agent, object, operation and domain-property views from Base Analysis.
- Keep primal Base Analysis facts distinct from overlay-specific anti-goals.
- Represent security-goal instantiation as a candidate-generating step.
- Record every anti-goal refinement with its rule, premises and proof status.
- Distinguish `informal_question`, `formal_regression` and `pattern_application` derivations.
- Represent anti-requirements and vulnerabilities as different candidate types.
- Record attacker capability and monitor/control assumptions explicitly.
- Mark attacker motives and missing domain properties as inferred.
- Preserve all alternative refinements and countermeasures before selection.
- Record selection criteria and rejected alternatives.
- Keep software requirements separate from environmental expectations.
- Add source-document provenance for every primal-model assertion.
- Add global coverage, stopping and incompleteness diagnostics.
- Re-run affected derivations when documents or Base Analysis facts change.
- Use later code and runtime evidence to confirm or contradict vulnerabilities and
  countermeasure assumptions.

## Candidate thesis claims

The source can support claims that a security analysis may begin from declarative stakeholder and
document assertions before implementation, and that structured goal models enable systematic
derivation of attacker goals, vulnerabilities and countermeasures. It cannot support claims that
raw documentation is sufficient, that the process is globally complete or terminating, that
automation replaces analyst judgment, or that the method is empirically superior.
