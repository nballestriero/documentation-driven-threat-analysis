## Why this source is central

This paper presents a pre-implementation security-requirements method built around functional
scenarios. It introduces misusers, misuse cases, security use cases and the `threaten` and
`mitigate` relationships, together with textual templates and a five-step elicitation process.

The source is directly relevant to DDTA because it shows how an existing functional view can be
turned into methodology-specific threat and security-requirement candidates without using source
code. It does not solve extraction of use cases, assets or goals from heterogeneous raw project
documentation.

## Four reading questions

### 1. Research problem and contribution

Ordinary use cases describe behavior that stakeholders want, but tend to neglect extra-functional
requirements and behavior that must not occur. The paper extends the use-case approach with:

- `misuser`: an intentional or inadvertent actor that initiates misuse;
- `misuse case`: an action sequence that causes harm if completed;
- `security use case`: a countermeasure or security requirement;
- `threaten`: relation from a misuse case to a threatened use case;
- `mitigate`: relation from a security use case to a misuse case.

The contribution combines notation, a metamodel, lightweight and extensive textual templates and
method guidelines.

### 2. Starting artifacts and system representation

The approach is designed for use-case-oriented requirements engineering. A code base or completed
design is not required. The five-step process nevertheless requires system knowledge:

1. critical assets;
2. security goals for each asset;
3. potential misusers and harmful action sequences;
4. risk and protection-cost assessments;
5. security requirements or countermeasures.

Use cases or equivalent functional scenarios provide the behavior that can be twisted, obstructed
or exploited. The paper does not explain how to derive those scenarios automatically from
requirements documents, architecture documents, decisions or other heterogeneous sources.

A lightweight representation adds a `Threats` field or column to each use case. An empty field
means security still requires investigation; an explicit low-probability or harmless-impact
statement records that the threat question was considered.

An extensive misuse-case description can include:

- basic and alternative harmful paths;
- mitigation points;
- trigger;
- assumptions and preconditions;
- mitigation guarantee;
- related business rules;
- misuser profile;
- scope and abstraction level;
- stakeholders and risks;
- technology or data variants.

### 3. Traceability, change, automation and human role

The method is manual and creativity-dependent. Stakeholders and analysts identify assets,
security goals, attackers, harmful paths, risks and countermeasures. Reusable repositories of
threats and requirements may support the process, but the paper provides no automatic extraction
or threat-generation algorithm.

The notation creates explicit links:

```text
use case
<- threatened by - misuse case
<- mitigated by - security use case
```

This links functional requirements to threats and links security requirements to the threats that
motivate them. The authors argue that these links support prioritization and change management.

The method also supports progressive refinement. Lightweight descriptions are recommended for
early brainstorming and lower-risk or simple twists. Extensive descriptions are recommended for
critical, complex or later-stage analysis. Each artifact can therefore retain an iteration and
abstraction level.

### 4. Findings, limitations and relationship with DDTA

The authors report use in research and realistic project settings, including an EU knowledge-map
project, a model-based risk-management framework used in six projects, stakeholder interviews and
trade-off analysis. The evidence is descriptive and heterogeneous; the paper does not provide a
common benchmark, controlled comparison, precision, recall or a conclusive large-scale industrial
evaluation.

The main strengths are early stakeholder-readable analysis, explicit links among functional and
security concerns, incremental detail and traceability.

The main weaknesses are:

- open-ended and imprecise method guidance;
- dependence on analyst improvisation and security knowledge;
- possible analysis paralysis from many assets and threats;
- underdeveloped prioritization and stopping criteria;
- limited fit for threats without an identifiable misuser or harmful action sequence;
- limited practical validation.

For DDTA, misuse cases are best modeled as a methodology overlay on a scenario view derived from
Base Analysis. They should not become mandatory canonical entities for every methodology.

## Research method and evidence

This is a method-synthesis and proposal paper, not an empirical comparative study. It consolidates
the authors' earlier work and emphasizes description and method guidelines.

Reported evidence includes:

- use for elicitation and discussion in an EU research project;
- embedding in a CORAS-oriented model-based framework used in six e-shop and telemedicine
  projects;
- stakeholder interviews on reusable misuse patterns;
- a reported industrial trade-off analysis by Alexander.

The paper itself states that more conclusive large-scale industrial validation is required.

## Five-step security-requirements process

### Step 1 - Identify critical assets

Assets include information possessed by the enterprise, virtual locations under enterprise
control and computerized activities performed by the enterprise.

### Step 2 - Define security goals

Each asset receives security goals, possibly aided by an existing security-goal taxonomy.

### Step 3 - Identify threats

Analysts identify stakeholders who may cause harm and action sequences that may cause intentional
or inadvertent harm. Threats can be documented as misusers and misuse cases.

### Step 4 - Analyze risks

Threats are assessed using risk and costing techniques. The paper does not define one mandatory
risk model.

### Step 5 - Define security requirements

Countermeasures are selected to match risk and protection cost, possibly with a taxonomy of
security requirements. They may be represented as security use cases.

The process is cyclic: new countermeasures can introduce new assets and new threats.

## Documentation-first classification

### Classification

`documentation_primary_structured_scenarios_required_or_created`

### Directly supported

- The method operates before coding and detailed design.
- Functional scenarios, assets and security goals are sufficient starting abstractions.
- Misuse cases can be documented textually without a formal model.
- Security requirements can be linked to threats and threatened functionality.
- Early and later iterations can use different levels of detail.

### Not supported

- Automatic extraction of use cases from raw project documentation.
- Automatic identification of all assets, misusers or threats.
- A complete neutral system model independent of the misuse-case methodology.
- A reliable global stopping rule or completeness guarantee.
- Quantitative evidence that the method outperforms alternative techniques.

## Main findings

- Negative scenarios can integrate security elicitation with ordinary use-case work.
- `threaten` and `mitigate` make the relationship among function, threat and countermeasure
  explicit.
- A lightweight threat field creates a visible per-use-case review status.
- Extensive templates preserve assumptions, preconditions, harmful paths, mitigation points,
  guarantees, stakeholders and risks.
- Security threats and requirements can be discussed before design choices.
- Progressive detail can concentrate effort on higher-risk scenarios.
- Traceability supports prioritization and later change management.
- The method remains strongly dependent on analyst creativity and expertise.

## Limitations

### Stated or acknowledged by the authors

- Guidelines remain general and imprecise.
- Developers must adapt and improvise.
- Many threats can lead to analysis paralysis.
- Prioritization and stopping guidance need further development.
- Not every threat has an identifiable actor or action sequence.
- Not every misuse threatens one identifiable use case.
- Practical validation remains limited.
- Misuse cases often need combination with other techniques.

### Additional limitations for DDTA comparison

- The method begins from structured scenarios rather than heterogeneous documentation.
- Source-to-scenario provenance is absent.
- It does not distinguish extracted documentation facts from analyst-created threat hypotheses.
- The threat model is centered on interaction sequences and can miss structural, systemic or
  non-scenario threats.
- It has no machine-readable diagnostic contract.
- It does not define cross-project evaluation or reproducibility artifacts.
- Current AI-assisted or continuous-analysis capabilities are outside the evidence window.

## Temporal validity

- Contribution type: foundational notation, template and procedure.
- Time sensitivity: medium for conceptual constructs; high for tooling and empirical maturity.
- Temporal status: foundational method evidence, not current comparative validation.
- Still applicable: scenario-based elicitation, typed relations, progressive refinement, explicit
  assumptions, stakeholder-readable analysis and threat-to-requirement traceability.
- Potentially obsolete: UML-specific presentation choices, historical tool assumptions and the
  empirical maturity described in 2005.
- Contemporary corroboration required: recent controlled studies, current misuse-case tooling,
  automated document understanding and comparison with modern threat-modeling workflows.
- Permitted thesis use: demonstrate a documentation-primary method for deriving threat and
  security-requirement candidates from structured scenarios. Do not use it as proof of
  completeness, automation or superiority.

## Relationship with Documentation-Driven Threat Analysis

### Directly supported propositions

- A first security analysis can precede code and detailed design.
- Functional scenarios can be transformed into negative security scenarios.
- Threats and security requirements should remain distinct linked entities.
- Assumptions, preconditions, harmful paths and mitigation guarantees are useful evidence fields.
- Analysis can progress from lightweight coverage to detailed high-risk cases.
- Trace links support explanation, prioritization and change management.

### Tensions

- The method is systematic at the representation level but open-ended at the discovery level.
- A visible per-use-case threat status does not provide a global completeness guarantee.
- Stakeholder-readable informality improves elicitation but weakens repeatability.
- Scenario focus improves accessibility but excludes some systemic threats.
- Reusable threat repositories can accelerate work but can also bias discovery toward known
  patterns.

### Research gap left open

The method assumes or creates structured use cases but does not govern the transformation from
heterogeneous documentation to assets, actors, goals, interactions and scenarios. It also lacks
explicit source provenance, confidence, completion diagnostics and comparative assurance.

### Overlay-method implications

- Require a declared scenario view rather than making use cases canonical Base Analysis entities.
- Declare required inputs: assets, actors, goals, activities, interactions and scope.
- Allow lightweight and extensive overlay profiles.
- Represent `misuser`, `misuse scenario`, `threatens` and `mitigated_by` as overlay concepts.
- Keep the accepted finding separate from the candidate misuse scenario.
- Keep mitigation candidates separate from accepted security requirements.
- Trace every scenario element to Base Analysis and ultimately to document evidence.
- Mark analyst-created misusers, harmful paths and assumptions as inferred.
- Record explicit `reviewed_no_material_threat` dispositions for covered scenarios.
- Add a global coverage and stopping rule not supplied by the source.
- Combine misuse-case analysis with structural and methodology-specific overlays.
- Re-run affected scenarios when source documentation or Base Analysis changes.
- Use later code evidence to confirm or contradict assumptions and mitigations.

## Candidate thesis claims

The source can support claims that scenario-based security analysis can begin before code and that
misuse cases create explicit links between functional behavior, harmful behavior and security
requirements. It cannot support claims that arbitrary documentation can be analyzed directly,
that threat coverage is complete, that the method is automated or that it is superior to other
threat-analysis techniques.
