## Why this source is central

This source supplies the broad evidence needed for the first transformation in a documentation-
driven workflow:

```text
natural-language requirements
+ optional domain knowledge, models, metadata or stakeholder feedback
-> automated or assisted processing
-> candidate UML, structured requirements or quality findings
-> human verification
```

It complements SRC-0031 and SRC-0032:

```text
SRC-0033: documentation -> candidate requirement/model artifact
SRC-0031: typed model -> candidate threats
SRC-0032: security test model -> abstract and executable security tests
```

The review demonstrates that document-to-artifact automation exists, but it does not establish a
trustworthy neutral model, complete semantics, maintained provenance or end-to-end autonomy.

## Four reading questions

### 1. Research problem and contribution

Natural-language requirements are central to software projects but are expensive and error-prone
to analyze manually. The SLR examines implemented tools with empirical evidence and asks:

1. what outputs or models are generated and what value is claimed;
2. which RE phase is most automated;
3. what degree of automation is reached;
4. which development techniques are used;
5. how tools are evaluated.

The search covers ACM, ScienceDirect, IEEE Xplore and Springer and was completed in December
2022. The selection flow is:

```text
3853 initial records
-> 425 after title screening
-> 268 after abstract screening and duplicate removal
-> 92 quality-assessed studies
-> 85 included studies
```

The review uses a yes/no quality assessment for minimum reporting quality, research-design
suitability, data analysis, credibility and relevance. Seven studies were removed.

Search, extraction and initial analysis were led by the first author; all authors participated in
review and quality analysis, and disagreements were resolved through discussion.

### 2. Starting artifacts and generated representations

Natural-language text accounts for 94 percent of tool input. It includes unstructured,
semi-structured and structured requirements. Other inputs include:

- domain knowledge;
- business-process models;
- existing models or artifacts;
- metadata;
- stakeholder feedback;
- voice input.

Most tools are one-shot transformations and only a small number are editor-style systems.

Thirty-eight studies, 44.7 percent, generate UML diagrams. The class or domain diagram is the most
common model, followed by use-case diagrams and structured requirements documents. Forty-seven
studies do not report a model output and instead support activities such as:

- omitted-step recommendation;
- consistency checking;
- validation and review;
- requirement classification;
- mining and extraction;
- duplicate detection;
- requirements reuse;
- security-related analysis.

The documentation-first classification is:

```text
documentation_primary
```

The input is often documentation itself, but the outputs are heterogeneous candidate artifacts,
not a common neutral Base Analysis.

### 3. Traceability, change, automation and human role

The recurring pipeline is:

```text
source document and segment
-> lexical preprocessing
-> syntactic parsing
-> semantic, rule or learned interpretation
-> extracted facts and inferred relations
-> candidate requirement or model artifact
-> expert correction and validation
```

The reported phase assignments are:

```text
analysis and specification: 53
elicitation:                 25
management:                 16
validation:                 13
total assignments:         107
```

The total exceeds the 85 studies because tools can span phases. The paper explains multi-phase
classification but does not explicitly explain the 107 denominator when presenting the percentages.
This is preserved as an open counting issue.

Automation levels are:

```text
semi-automated: 50 studies, 58.8%
fully automated: 35 studies, 41.2%
```

Human intervention may occur in input preprocessing, refinement during processing and output
interpretation. Even tools labelled fully automated produce an artifact for human verification;
none proposes full replacement of the requirements engineer.

The authors also classify automation across:

1. information acquisition;
2. information analysis;
3. decision selection;
4. action implementation.

Information analysis has the highest reported automation. DDTA should therefore declare
automation separately for each stage.

Traceability is not established as a common capability. The authors explicitly call for links
from formalized model elements back to original statements and for maintained links among
requirement elements and produced artifacts.

Most tools are one-shot. Model evolution, agile integration, interoperability, context adaptation
and change synchronization remain future directions. No evaluated stale-detection workflow is
reported.

### 4. Findings, limitations and relationship with DDTA

#### Main findings

- natural-language input: 94 percent;
- UML output: 44.7 percent;
- analysis/specification assignments: 49.53 percent of 107 assignments;
- semi-automated tools: 58.8 percent;
- NLP as primary development approach: 50.6 percent;
- controlled-experiment category: 48.2 percent;
- user studies: 8.2 percent.

NLP technologies include POS tagging, tokenization, parsing, lemmatization, stemming, sentence
splitting and morphological analysis. Machine-learning techniques include Naive Bayes, KNN, SVM,
neural networks and decision trees. Ontologies, information retrieval, data mining and text mining
also appear.

#### Evaluation evidence

```text
controlled experiment: 41
case study:           25
prototype / PoC:      12
user study:            7
```

The controlled-experiment category is heterogeneous. It includes both limited illustrative
examples and deeper studies using industrial data. The counts do not establish comparable rigor.

User-centered evidence is sparse. Technical accuracy, practical usefulness, usability and
organizational adoption are therefore separate outcomes.

#### Main limitations

- possible subjective selection and classification;
- possible missing studies and search-string sensitivity;
- four databases but no stated preregistered protocol;
- first-author concentration in search, extraction and analysis;
- binary quality-assessment scheme;
- no meta-analysis;
- no common benchmark dataset;
- no direct cross-tool comparative evaluation;
- limited industrial deployment and practitioner feedback;
- geographic concentration in Europe and Asia;
- emphasis on functional requirements;
- evidence horizon ends before modern generative-LLM adoption.

## Core definitions

### Automated requirements engineering

Tool-supported partial or complete execution of requirements elicitation, analysis,
specification, validation or management activities.

### Candidate requirement artifact

A structured requirement, classification, model element, quality finding or diagram generated
from source inputs and requiring validation before acceptance.

### Semi-automated support

A workflow in which analysts participate in preprocessing, intermediate refinement, decision
making or output interpretation.

### Fully automated transformation

A transformation step that runs without human intervention once invoked. It does not imply an
autonomous end-to-end RE process or removal of expert validation.

### One-shot tool

A tool that accepts an input and produces an output in a discrete run rather than maintaining an
interactive, continuously synchronized editing environment.

## Traceability, change, automation and human role

### Traceability present

Individual tools may provide source-to-output links, but the review does not establish a common
or widely implemented traceability mechanism. Traceability is explicitly proposed as future work.

### Change

The review identifies model evolution, agile integration, context adaptation and interoperability
as open research implications. Most tools are one-shot and no longitudinal synchronization result
is established.

### Automation

Automation is strongest in information analysis. Inputs and outputs, pipeline stages and human
interventions vary significantly across tools.

### Human review

Human experts remain responsible for validating generated artifacts, resolving ambiguity,
correcting models, deciding acceptance and using the output in subsequent development phases.

## Documentation-first classification

### Classification

`documentation_primary`

Natural-language requirements are the dominant direct input, but documentation may be augmented
by domain knowledge, existing models, metadata and stakeholder feedback.

### Nine documentation-first fields

1. Input and quality: mostly natural-language text; ambiguity, inconsistency and input standardization are open issues.
2. Compatibility: `documentation_primary`, with heterogeneous supplemental inputs.
3. Intermediate representation: linguistic facts, classifications, domain concepts, relations and model elements.
4. Procedure: preprocessing, parsing, interpretation, mapping, generation and human validation.
5. Output: candidate UML, structured requirements and RE quality findings.
6. Provenance, uncertainty, review: traceability is not common; confidence and extracted/inferred states are not standardized.
7. Evolution/change: mostly one-shot tools; model evolution and synchronization remain open.
8. Evaluation/evidence: 85 heterogeneous empirical studies with a binary quality gate.
9. Thesis use: evidence for document-to-candidate-artifact automation and its provenance/human-review boundary.

## Directly supported

- Natural-language requirements are direct inputs to many automated-RE tools.
- Automatic and semi-automatic document-to-artifact transformations have been implemented.
- UML, especially class diagrams, is a common output.
- NLP is the dominant development technique in the reviewed corpus.
- Analysis and specification receive the most automation assignments.
- Most tools are semi-automated.
- Human verification remains necessary after fully automated transformations.
- Most tools are one-shot rather than continuously synchronized editors.
- Traceability and model evolution remain research gaps.
- Industrial adoption, user studies and comparative benchmarks are limited.

## Not supported

- Generated models are complete or semantically correct.
- Every input assertion is represented in the output.
- Fully automated tools replace requirements engineers.
- Traceability is normally preserved.
- Tools reliably resolve contradictory or missing documentation.
- Outputs remain synchronized after source changes.
- Results can be compared through a common benchmark.
- Automated-RE tools are widely adopted in industry.
- Functional-requirement results generalize to security and other non-functional requirements.
- The review represents generative-LLM-based RE in 2026.

## Eight DDTA evidence questions

1. Documents sufficient without code: often yes for a candidate artifact; no for guaranteed completeness or correctness.
2. Neutral intermediate representation: not defined; tools produce heterogeneous facts, models and findings.
3. Extracted versus inferred: not standardized.
4. Method as overlay: NLP, ML, ontology and rule pipelines behave as transformation components.
5. Provenance, confidence, review: traceability is a stated gap; confidence and review states are not normalized.
6. Documentation change: mostly one-shot; synchronization and model evolution remain open.
7. Later code evidence: outside the main scope; outputs support downstream design and development.
8. Measurement: heterogeneous experiments and cases; no common benchmark or uniform cross-tool metrics.

## Relationship with Documentation-Driven Threat Analysis

### Base Analysis implications

DDTA should preserve:

- source document identity and version;
- source segment or assertion;
- extracted linguistic facts;
- inferred entities and relationships;
- domain knowledge and assumptions;
- transformation technique and version;
- candidate model element;
- confidence and alternatives;
- reviewer disposition and corrections;
- downstream accepted Base Analysis element;
- stale status after source changes.

### Transformation-plugin implications

A documentation-processing plugin should declare:

- accepted document types and languages;
- preprocessing pipeline;
- extraction and inference schemas;
- model, rules, ontology or prompt version;
- required external domain knowledge;
- output artifact schema;
- source-link granularity;
- confidence semantics;
- human-intervention points;
- supported and unsupported requirement types;
- evaluation task and metrics;
- update and stale-detection behavior.

### Candidate-artifact lifecycle

```text
source accepted
-> extraction executed
-> candidate generated
-> review pending
-> accepted | corrected | rejected | deferred
-> Base Analysis element linked
-> stale after source or transformer change
-> regenerated and re-reviewed
```

DDTA must not silently promote a generated model element into canonical project knowledge.

## Candidate thesis claims

Supported directly or conditionally:

- Natural-language requirements can be processed into candidate structured artifacts.
- Generated models require human verification and should retain source provenance.
- Automation level should be declared per pipeline stage.
- One-shot transformations require explicit stale detection and regeneration.
- Automated RE can reduce initial modelling effort without replacing expert judgment.
- Common benchmark cases are necessary for comparative evaluation.

Not supported:

- DDTA can construct a complete and correct Base Analysis automatically.
- A generated UML diagram is a faithful canonical representation by default.
- Full automation removes stakeholder or analyst involvement.
- Classical NLP results establish modern LLM performance.
- A model remains valid when documentation changes.
- Functional-requirement results guarantee security-requirement extraction quality.

## Research gap left open

The review establishes broad document-to-artifact feasibility but does not provide a common
provenance model, uncertainty semantics, contradiction handling, update protocol or benchmark
for constructing a trustworthy neutral Base Analysis. It also predates widespread generative
LLM use and therefore does not resolve how prompt-, retrieval- and model-version changes should
be governed.

The next source should narrow the transition from requirements artifacts to software
architecture and preserve traceability between them.
