## Why this source is central

This review provides a systematic comparison framework for threat-analysis techniques. It
separates applicability, required input, procedure, outcomes, ease of adoption and validation.
These dimensions are directly useful for constructing the DDTA state-of-the-art matrix.

The review does not study automatic extraction from raw documentation. It generally starts after
the available information has already been expressed as goals, requirements, textual system
descriptions, attack assumptions, scenarios or architectural models. This boundary is the most
important finding for the documentation-first research question.

## Four reading questions

### 1. Research problem and contribution

The paper addresses the difficulty of selecting among many threat-analysis approaches. It
systematically reviews 38 primary publications representing 26 techniques and compares them using
criteria covering:

- applicable abstraction level;
- input type and representation;
- procedure and precision;
- security objectives and risk;
- outcome type, representation and quality assurance;
- tool support, guidance and analyst expertise;
- validation type, validator and domain.

The search starts from 5,000 ranked results and ends with 38 primary studies after three filtering
stages and backward snowballing.

### 2. Starting artifacts and system representation

The review distinguishes requirements, attacker behavior, security assumptions, architectural
design, source code and high-level goals as input types. Input may be represented by textual
descriptions, models or other forms.

The authors state that threat analysis requires knowledge of:

1. what the system is, such as architecture, source code or functional requirements;
2. what it is protected from, such as attacker behavior or security assumptions.

Across the reviewed publications:

- 14 techniques are applicable at requirements level;
- 11 at architectural level;
- 13 at design level;
- only two at implementation level;
- 12 publications use architectural design as input;
- 11 use requirements;
- six use attacker behavior;
- seven use security assumptions;
- five use high-level goals;
- only one technique considers source code, and there it is optional;
- 15 use textual descriptions;
- 11 use models;
- four use both.

This is strong evidence that early threat analysis normally does not require code. It is not
evidence that unstructured project documentation is sufficient without interpretation or model
construction.

### 3. Procedure, automation and human role

The paper distinguishes risk-centric, attack-centric and software-centric techniques, while also
identifying goal-oriented requirements engineering, security requirements engineering and
privacy-specific approaches.

About half of the techniques use a knowledge base. Procedure precision is often limited to
examples or templates. Four technique families are classified as formal or very precise, six are
semi-automated and about seven do not address procedure precision.

Threat identification and prioritization remain expert activities even when tools are available.
Graphical tools often help construct diagrams but do not assure correctness or completeness.
Knowledge bases, automation and structured guidance can reduce the required expertise but do not
replace semantic judgment.

### 4. Findings, limitations and relationship with DDTA

All reviewed techniques produce threats. Fifteen also produce mitigations, twelve produce
security requirements and eight produce all three. Most outcomes remain high-level.

Quality assurance is weak:

- only three techniques include explicit quality assurance;
- five include some non-explicit assurance;
- seventeen have no identified quality assurance.

Tool and validation maturity are also limited:

- eleven techniques have no tool support;
- eleven have tools;
- four have prototypes;
- nineteen use case studies under the review's broad definition;
- eight include experiments;
- nine use illustrations.

The authors identify missing Definition of Done, vague procedures, weak quality assurance,
immature tools and limited validation. For Agile and DevOps they identify traceability,
composability and automated threat-impact analysis as open directions.

For DDTA, this source supports an explicit contract for input, procedure, output, completion and
verification. It does not provide the documentation-to-Base-Analysis transformation that DDTA
needs before applying a methodology overlay.

## Research method and corpus

- Systematic literature review following Kitchenham-style guidance.
- Automatic search in ACM, IEEE Xplore and Google Scholar.
- Search executed in January 2017.
- Initial ranked pool: 5,000 results.
- After title and keyword filtering: 136.
- After abstract and conclusion filtering: 62.
- After full-text filtering: 31.
- After backward snowballing: 38 primary studies.
- Final comparison: 26 techniques.
- Venues below CORE rank B were excluded.
- Grey literature, short papers, safety-hazard analysis, anomaly detection and intrusion detection
  were excluded.
- One researcher performed the main selection and extraction.
- Ten-percent random checks were performed by a second researcher.
- Five papers were independently re-extracted; six discrepancies across 67 assessments were
  discussed and the remaining papers were then rechecked.

## Taxonomy of technique focus

### Risk-centric

The analysis is organized around assets, organizational value, risk and residual-risk reduction.
Assets determine the priority of security requirements.

### Attack-centric

The analysis is organized around attacker profiles, hostile actions, attack paths and threat
coverage.

### Software-centric

The analysis is organized around the software representation, such as STRIDE applied to DFD
elements.

### Requirements and privacy families

The review also uses GORE, SRE and privacy labels because some approaches do not fit cleanly into
the three focus categories.

## Documentation-first classification

### Directly supported

- Early threat analysis can operate at requirements, architecture and design abstraction levels.
- Requirements, goals and textual descriptions are common inputs.
- Source code is rarely required in the reviewed corpus.
- Threat analysis may be repeated later in the lifecycle.
- Many techniques produce security requirements from threats and mitigations.

### Researcher interpretation for DDTA

The review describes methods that can start before implementation, but usually assumes that
someone has already created a suitable requirements, goals, scenario or architecture
representation. Therefore the documentation-first pipeline has two distinct problems:

```text
project documentation
-> governed Base Analysis representation
-> threat-analysis technique or methodology overlay
```

The first transformation is not solved by this review. The second is the subject of most of the
reviewed techniques.

### Classification consequence

- Requirements, goals and textual system descriptions are `documentation_primary`.
- DFD, UML, sequence and architectural models are `documentation_plus_model`.
- The reviewed implementation-level methods are `code_optional_or_required`.
- No reviewed category establishes automatic `raw_documentation_to_neutral_model`.

## Main findings

- No code is needed for most reviewed early-analysis approaches.
- Attack-centric approaches form the largest family.
- Requirements-engineering methods form another substantial family.
- Most procedures are not defined precisely enough to guarantee repeatability.
- Stopping conditions are generally absent.
- Threat identification and prioritization remain expert-driven.
- Tool support commonly aids representation rather than semantic threat discovery.
- Quality assurance is absent in most methods.
- Empirical validation is limited and concentrated in Web systems.
- Method selection depends on resources, expertise, input artifacts and desired assurance.
- STRIDE and LINDDUN are systematic but risk threat explosion because they visit each DFD element.
- Requirements-engineering approaches may be easier to adopt but often lack outcome guarantees.

## Limitations stated or implied by the review

- The evidence window ends before January 2017.
- The search emphasizes venues with CORE rank B or higher.
- Grey literature and industrial method documentation are excluded.
- Main selection and extraction were conducted by one researcher with sampled checks.
- The authors use a broad definition of case study that includes many real-world applications
  lacking rigorous case-study design.
- The review does not measure comparative effectiveness under a common benchmark.
- The review does not evaluate automatic extraction from raw documents.
- Tool availability and maturity observations are historically dated.
- AI-assisted and LLM-based methods are outside the evidence window.

## Temporal validity

- Contribution type: systematic review and comparison taxonomy.
- Time sensitivity: high for tools, automation and adoption; medium for conceptual categories.
- Temporal status: historical systematic baseline, not a current state-of-the-art review.
- Still applicable: separation of input, procedure, output, assurance, adoption and validation;
  early abstraction levels; need for Definition of Done; need for explicit quality assurance.
- Potentially obsolete: tool availability, degree of automation, DevOps integration and method
  maturity as observed before 2017.
- Contemporary corroboration required: recent automated-tool reviews, current threat-modeling SLRs,
  continuous threat analysis and AI-assisted documentation analysis.
- Permitted thesis use: establish the historical taxonomy and longstanding gaps. Do not use it to
  claim the current maturity of tools or the complete set of methods available in 2026.

## Relationship with Documentation-Driven Threat Analysis

### Directly supported propositions

- Threat analysis is primarily an early-design activity and may be repeated later.
- Requirements and textual descriptions can be valid inputs.
- Code is not normally required for the first analysis.
- Techniques differ materially in required artifacts, procedure precision, outcomes and assurance.
- Threats, mitigations and security requirements are distinct outputs.
- Completion and quality criteria are commonly missing.

### Tensions

- Methods can begin early, but the review still requires knowledge of what the system is.
- Textual input is common, but raw-document extraction is not addressed.
- Tools are available, but many only structure diagrams or templates.
- Systematic element-by-element analysis can increase coverage while causing threat explosion.
- Lightweight requirements methods improve adoption while weakening assurance.
- Formal methods improve precision but increase expertise and resource requirements.

### Research gap left open

The review leaves open a governed transformation from heterogeneous documentation to a neutral,
versioned and reviewable system representation, followed by methodology-specific analysis with
explicit provenance, uncertainty, completion conditions and quality evidence.

### Overlay-method implications

- Separate Base Analysis construction from methodology execution.
- Declare accepted input artifact types for every overlay.
- Record whether an input fact is extracted, supplied or inferred.
- Require explicit source-to-model provenance.
- Define a stopping condition and coverage report.
- Keep threats, findings, mitigations and security requirements distinct.
- Add explicit verification of analysis outputs.
- Preserve human acceptance for semantic conclusions.
- Support requirements-level analysis without code.
- Add code only as a later corroborating or contradictory evidence source.
- Evaluate lightweight and systematic modes separately.
- Measure threat explosion and analyst workload.

## Candidate thesis claims

The source can support claims that pre-implementation threat analysis commonly uses requirements,
goals, textual descriptions and architecture models, while source code is rarely required. It can
also support claims that procedures, quality assurance, completion criteria, tools and validation
were weak in the pre-2017 literature. It cannot support claims that raw documentation is
automatically sufficient, that a neutral Base Analysis already exists in the literature, or that
the same maturity gaps remain unchanged in 2026.
