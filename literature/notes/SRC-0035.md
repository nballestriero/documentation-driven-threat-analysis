## Why this source is central

SRC-0035 provides the recent empirical boundary that SRC-0033 and SRC-0034 leave open:

```text
natural-language requirements
-> general-purpose LLM
-> candidate UML behavioral view
-> syntax, coverage, semantic and trace validation
-> human correction and acceptance
```

It shows that an LLM can rapidly create a readable, renderable and terminologically plausible
sequence diagram from realistic requirements. It also shows why this output cannot be promoted to
canonical Base Analysis or architectural evidence without independent validation: missing content,
incorrect interactions, hidden contradictions, unsupported terms and incomplete traceability occur
behind visually convincing output.

## Four reading questions

### 1. Research problem and contribution

Natural-language requirements are common, while graphical models require substantial manual effort.
The paper evaluates whether ChatGPT can assist by producing UML sequence diagrams, which represent
behavioral interactions and complement static class diagrams.

The two research questions are:

1. what is the quality of generated sequence diagrams;
2. what issues emerge during generation.

The contribution is a quantitative five-criterion assessment plus a qualitative taxonomy of 23
issue categories. It is not a proof of autonomous or correct model construction.

The diagrams are abstract stakeholder-communication artifacts. Message labels use free-form text
rather than executable pseudo-code.

### 2. Starting artifacts and generated representations

The study selects 28 industrial requirements documents from:

- Ten Lockheed Martin Cyber-Physical Challenges;
- PURE requirements dataset;
- a user-story dataset.

The documents cover 18 domains and three formats:

```text
shall requirements
use-case specifications
user stories
```

Only functional requirements are included. The findings do not directly establish quality for
security, privacy or other non-functional requirements.

Researchers construct 87 variants:

```text
17 shall subsets  -> 57 variants
7 use cases       -> 17 variants
4 user-story docs -> 13 variants
```

Variants add, remove or modify requirements and introduce ambiguity, inconsistency and
incompleteness. Variant generation is intuitive and non-systematic, and the order of evaluation can
bias the issue set.

The transformation is:

```text
selected requirement subset
-> one visualization-generator prompt
-> GPT-3.5 through ChatGPT web
-> PlantUML text
-> PlantText rendering
-> abstract UML sequence diagram
```

Separate sessions are used, and only the first output is included in the evaluated results. Later
correction prompts are outside the quantitative study.

The documentation-first classification is:

```text
documentation_direct_single_shot_llm_projection
```

No neutral intermediate representation is constructed and validated before the diagram. Extracted
facts, inferred relations, abstraction choices and unsupported additions can coexist in one output.

### 3. Traceability, change, automation and human role

#### Five quality dimensions

Each diagram is scored from 1 to 5 for:

- completeness;
- correctness;
- adherence to the standard;
- understandability;
- terminological alignment.

The operational standard gate uses PlantText parsing and appropriate use of constructs. The paper
explicitly warns that PlantText may not implement every nuance of UML; parser acceptance is therefore
not full UML certification.

#### Quantitative results on well-formed inputs

| Criterion | Mean | p-value | Cohen d |
|---|---:|---:|---:|
| Completeness | 3.634146 | 0.003652 | 0.503258 |
| Correctness | 3.219512 | 0.101543 | 0.194357 |
| Standard adherence | 4.536585 | 1.4E-07 | 1.572471 |
| Understandability | 4.365854 | 6.35E-07 | 1.227660 |
| Terminology | 4.487805 | 2.13E-07 | 1.447751 |

Correctness is the only criterion not significantly above the neutral value. Completeness is better
but still includes many non-maximal scores.

```text
renderable + understandable + familiar terminology
!= complete + correct + source-faithful
```

Thirty models are cross-evaluated, producing square-weighted Cohen's kappa `0.67`. This partially
supports evaluator consistency but does not remove subjectivity.

#### No canonical gold standard

The researchers do not create one reference diagram because several sequence diagrams can satisfy
the same requirements. Correctness is assessed through expert comparison with the source. DDTA should
therefore validate source coverage and semantics without requiring one unique layout.

#### Traceability

ChatGPT sometimes adds notes or requirement identifiers, but traces can be incomplete or wrong. A
trace label generated inside the model is not verified provenance.

```text
source assertion
-> proposed model element link
-> independent coverage and semantic verification
-> accepted trace
```

#### Change and session state

The authors observe apparent influence from prior interactions and cases where requirement changes
are ignored. They also observe output variability for the same query. Model provider, model ID,
interface, prompt, session, memory and context are therefore execution provenance.

#### Human role

The analyst remains responsible for:

- checking requirement quality;
- decomposing behavior into modelable steps;
- probing the LLM's understanding;
- adding domain and contextual knowledge;
- comparing every relevant source assertion with the output;
- correcting or regenerating the model;
- selecting among acceptable alternatives;
- approving, rejecting or deferring the diagram.

### 4. Findings, limitations and relationship with DDTA

#### Main failure families

##### Completeness

- excessive summarization;
- omitted requirement fragments;
- missing components, calls, messages and conditions;
- hidden ambiguity and inconsistency;
- poor handling of numbers, timing and mathematical constraints.

##### Correctness

- wrong interaction order or flow;
- incorrect actors and components;
- data represented as an actor;
- missing states and control loops;
- wrong assignment of responsibility;
- arbitrary selection among conflicting requirements.

##### Notation and terminology

- parser errors;
- semantically incorrect constructs;
- unsupported new terms;
- missing relevant terms;
- unrecorded renaming or synonym substitution.

##### Understandability and general issues

- incomplete trace notes;
- incoherent conditions;
- misplaced notes;
- redundant details or actor overrepresentation;
- hallucination;
- ignored modifications;
- insufficient domain context;
- output variability.

#### Limitations

- one provider/model family: GPT-3.5;
- ChatGPT web interface without an immutable model snapshot;
- one prompt pattern;
- first output only;
- sequence diagrams only;
- functional requirements only;
- expert-constructed non-systematic variants;
- no manually defined gold standard;
- subjective scoring despite cross-evaluation;
- possible memory or session-state interference;
- no systematic mapping from each mutation to each issue;
- no direct measurement of iterative correction cost;
- no comparison with modern 2026 models.

## Core definitions

### LLM-generated candidate model

A structural or behavioral model projection produced by a generative model from selected project
evidence. It is not canonical project knowledge until its syntax, source coverage, semantics and
traces have been reviewed.

### Source coverage

The verified relationship between relevant source assertions and generated model elements,
including represented, omitted, contradicted, added and intentionally abstracted content.

### Semantic validation

Evaluation that actors, components, responsibilities, interactions, states, conditions, quantities
and ordering accurately reflect the governed source and accepted domain knowledge.

### Session provenance

The recorded provider, model, snapshot, interface, prompt, parameters, conversation state, memory,
external context and generation timestamp that may affect output.

## Traceability, change, automation and human role

### Traceability present

Occasional generated notes and requirement identifiers are observed, but they can be incomplete or
incorrect. Traceability requires independent verification.

### Change

Requirement variants expose ignored modifications and possible prior-session influence. A generated
model becomes stale after any source, prompt, model, context or acceptance-rule change.

### Automation

The generation step is automatic once prompted. Input selection, decomposition, contextualization,
validation, correction and acceptance remain human or separately automated responsibilities.

### Human review

Human review is the principal assurance mechanism in the evaluated workflow. The model is an
assistant-generated candidate, not an autonomous decision.

## Nine documentation-first fields

1. Input and quality: realistic functional requirements with explicit quality defects and changes.
2. Compatibility: direct documentation input; no code required.
3. Intermediate representation: implicit model interpretation inside GPT-3.5; no governed neutral IR.
4. Procedure: select, prompt, generate PlantUML, render, score, inspect and categorize issues.
5. Output: abstract candidate UML sequence diagram.
6. Provenance, uncertainty, review: prompt/log evidence exists; source traces may be incomplete; no confidence semantics.
7. Evolution/change: variants are tested; modifications may be ignored; no maintained synchronization.
8. Evaluation/evidence: 28 documents, 87 variants, expert scores, kappa and thematic analysis.
9. Thesis use: LLM candidate-model boundary and syntax/source/semantic/trace validation contract.

## Directly supported

- GPT-3.5 can generate understandable sequence-diagram candidates from realistic requirements.
- PlantUML-oriented syntax and terminology often appear strong.
- Correctness and completeness remain the principal quality problems.
- Ambiguity and inconsistency may be hidden instead of surfaced.
- Numbers, timing, states and loops are high-risk information.
- Generated trace annotations can be incomplete or inaccurate.
- Domain context and iterative prompting can improve a human-in-the-loop process.
- Multiple valid diagrams may exist for one requirement set.
- Session state and output variability affect reproducibility.
- Expert validation remains necessary.

## Not supported

- Generated diagrams are complete or correct by default.
- A clear diagram is semantically faithful.
- PlantText acceptance proves full UML compliance.
- Generated trace labels establish complete provenance.
- Requirement conflicts are reliably detected.
- Requirement changes are reliably propagated.
- Output is deterministic across runs.
- Findings generalize to NFRs or security requirements.
- Findings generalize to every LLM or current 2026 models.
- The workflow can replace an experienced requirements analyst.

## Eight DDTA evidence questions

1. Documents sufficient without code: yes for candidate behavioral diagrams, not for guaranteed fidelity.
2. Neutral intermediate representation: absent; interpretation is hidden inside the model.
3. Extracted versus inferred: mixed in one output and not explicitly labelled.
4. Method as overlay: LLM generation is a replaceable projection plugin over selected source evidence.
5. Provenance, confidence, review: prompt and logs are available; trace and confidence need separate governance.
6. Documentation change: explicitly challenged, but synchronization can fail and session state can interfere.
7. Later code evidence: outside this study; code can later corroborate or contradict the accepted model.
8. Measurement: five expert-scored dimensions, cross-evaluation and 23 issue categories; no gold-standard accuracy.

## Relationship with Documentation-Driven Threat Analysis

### LLM model-generation plugin contract

A plugin should declare:

- accepted source document and requirement types;
- selected source assertions and exclusions;
- preprocessing and decomposition;
- provider, model ID, snapshot and interface/API version;
- system prompt, user prompt and templates;
- sampling and generation parameters;
- session, memory and conversation state;
- external context, glossary and domain knowledge;
- output notation, schema and renderer/parser version;
- generated textual source and rendered representation;
- proposed assertion-to-element traces;
- added, omitted, renamed and contradicted concepts;
- syntax and notation-semantic validation results;
- source-coverage and behavioral-semantic validation results;
- alternatives and output variability;
- human corrections, reviewer and disposition;
- stale triggers and regeneration policy.

### Candidate lifecycle

```text
source subset accepted
-> generation context frozen
-> candidate PlantUML generated
-> parser validation
-> source-coverage validation
-> semantic and domain validation
-> trace validation
-> human review pending
-> accepted | corrected | rejected | deferred
-> stale after source, prompt, model, context or rule change
-> regenerated and re-reviewed
```

### Thesis implication

A model that renders successfully and looks plausible may still omit a security-relevant condition,
hide a contradiction, invent a component or assign behavior to the wrong actor. DDTA must preserve
the source as authority and treat every generated model as a reviewed projection.

## Candidate thesis claims

Supported directly or conditionally:

- LLMs can reduce the effort of producing first-pass behavioral models from requirements.
- Generated model quality must be decomposed into syntax, coverage, semantics, terminology and usability.
- Source defects can be hidden by a coherent-looking generated model.
- Assertion-level provenance and explicit omission/addition reporting are necessary.
- Human-in-the-loop clarification and correction are integral parts of the process.
- Model and session provenance are required for reproducibility and change control.

Not supported:

- DDTA can construct a trustworthy behavioral model from one prompt without review.
- A high understandability score implies correctness.
- One canonical sequence diagram is required for every requirement set.
- GPT-3.5 results establish modern multi-model performance.
- Generated behavioral models automatically cover security-relevant NFRs.

## Research gap left open

The study does not compare multiple current models, use a gold-standard assertion-to-model mapping,
evaluate security or other NFRs, measure iterative correction effort, freeze a reproducible API
configuration or test maintained synchronization over a longitudinal project history.

The next source should provide a multi-model, contemporary comparison of LLM-based UML generation or
requirements modelling.
