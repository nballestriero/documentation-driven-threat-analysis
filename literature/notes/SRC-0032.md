## Why this source is central

This source closes the dedicated model-based security testing branch of the central corpus.
It explains the artifacts and transformation stages needed to move from security-enriched models
to abstract tests, concrete executable tests and observed evidence.

Its main automation boundary is:

```text
model of the SUT or environment
+ security properties
+ optional attack or threat model
+ test-selection criterion
-> abstract security test
-> concretization and adapter
-> executable test
-> observed result
```

The review does not establish automatic transformation from heterogeneous project documentation
into a trustworthy test model. It therefore complements SRC-0031:

```text
SRC-0031: typed model -> candidate threats
SRC-0032: security/test model -> abstract and executable security tests
```

## Four reading questions

### 1. Research problem and contribution

IoT security testing is difficult because devices, firmware, software, protocols, interfaces and
deployment contexts are heterogeneous and evolving. Manual security-test design is expensive, while
model-based testing can systematize and partially automate test derivation.

The review asks:

1. which formalisms are used for model specification;
2. which testing objectives are pursued;
3. which test-generation and execution techniques are used;
4. which IoT applications and domains are targeted;
5. which attacks are targeted;
6. which gaps and future directions remain.

The authors use a Rapid Review rather than a full SLR. The method is systematic but intentionally
simplified for timeliness. The selection process considers 803 publications and includes 17 primary
studies.

The search flow is:

```text
November 2021 Scopus search: 667
-> title/abstract/keyword screening: 84
-> full-text inclusion: 13
-> snowballing additions: 3
-> first-round corpus: 16

April 2022 update: 116 new records
-> title/abstract/keyword screening: 15
-> full-text inclusion: 1
-> final corpus: 17
```

Every selected full text was read by at least two authors and classification disagreements were
discussed collectively. No formal quality assessment of primary studies was conducted.

### 2. Starting artifacts and representation

The general MBT process starts from requirements, specifications or an existing SUT and builds a
test model. Test-selection criteria reduce the test space. Generated tests are initially abstract
and implementation-independent, then require translation and adaptation for execution.

The most common representations are:

- UML class diagrams: 7 of 17 studies;
- UML with OCL: 6 of the 7 UML studies;
- timed automata and extensions: 5 of 17;
- attack trees: 4 of 17 as supplementary attack models;
- hierarchical colored Petri nets;
- BPMN;
- topology graph;
- data flow graph;
- MACM;
- Mealy machines learned from observations.

UML class diagrams describe entities and dependencies. OCL supplies operations, parameters,
preconditions, postconditions and expected behavior. Security profiles add protected properties,
protocols or attack-surface stereotypes. Timed automata add clocks and temporal constraints.
Attack trees describe attacker strategies and can be transformed into price timed automata.

The documentation-first classification is:

```text
model_required
```

Requirements and specifications may inform model construction, but the review does not evaluate
automatic extraction of test models from heterogeneous documents.

### 3. Traceability, change, automation and human role

A useful evidence chain derived from the review is:

```text
security requirement
-> model property or constraint
-> attack model / threat template
-> test-selection criterion
-> abstract test
-> concrete test and adapter
-> execution environment
-> observed result
-> conformance or vulnerability judgment
```

Automation is strongest after the model and test objective exist:

- OCL structural coverage and symbolic exploration;
- reachability analysis and model checking;
- attack-tree path coverage;
- test-purpose transformation;
- model-guided fuzzing;
- model-guided penetration testing;
- automata learning;
- generation of TTCN-3 and other executable artifacts.

More than 40 percent of the reviewed studies use model-coverage criteria. Almost 30 percent combine
formal verification with model-based testing. More than 30 percent combine MBT with another strategy,
including penetration testing, fuzzing or model inference.

Abstract test generation does not remove human work. Humans still define or validate the model,
security properties, attack model, test purposes, adapters, testbeds, oracles and result
interpretations.

The review recognizes regression and reuse benefits of MBT but identifies dynamic evolution,
context awareness, heterogeneous devices and model maintenance as unresolved problems.

### 4. Findings, limitations and relationship with DDTA

#### Main findings

- UML with OCL is the most frequent representation family.
- Timed automata are the second most frequent formalism.
- Test-generation technique strongly depends on model formalism.
- Ordinary behavioral model coverage is insufficient for all security objectives.
- TTCN-3 is the most common abstract test format, used in about 40 percent of studies.
- TITAN is the most frequently reported execution tool.
- Test adapters connect abstract test messages to concrete SUT interactions.
- Automotive and smart cities are the most represented domains, with three studies each.
- Denial of Service is targeted by eight studies.
- The reviewed studies cover about 40 percent of the adopted IoT attack taxonomy.

#### Main limitations

- Rapid Review rather than full SLR.
- Automated search limited to Scopus.
- Google Scholar used only for snowballing.
- No primary-study quality assessment.
- No risk-of-bias scoring or meta-analysis.
- Search horizon ends in April 2022.
- Only 17 primary studies.
- Studies are mostly exploratory.
- Large realistic comparative case studies are missing.
- Data are available only on request.

## Core definitions

### Model-based testing

Automatic or systematic derivation of tests from one or more explicit models of the SUT or its
environment, according to test-selection criteria.

### Model-based security testing

Model-based testing whose test objectives and model semantics address security requirements such
as authentication, authorization, confidentiality, integrity or resistance to specified attacks.

### Test model

A formal or semi-formal representation containing the SUT behavior, structure, environment,
constraints or security properties required for test derivation.

### Test-selection criterion

A rule used to select a finite set of tests from model behavior, such as structural coverage,
reachability, state or transition coverage, attack-tree coverage or an explicit security test purpose.

### Abstract test

An implementation-independent sequence, tree, scenario or test case derived from the model.

### Test concretization

Translation of an abstract test into technology- and environment-specific actions, values and scripts.

### Test adapter

A component that maps abstract test messages and operations to concrete SUT interfaces and maps
observed responses back to the test framework.

### Test oracle

A rule or mechanism that determines whether observed behavior satisfies the expected security or
conformance condition. The review does not provide a cross-study oracle taxonomy.

## Traceability, change, automation and human role

### Traceability present

The primary studies can support links among model entities, security properties, test purposes,
abstract tests and generated scripts. The review does not define a common provenance schema,
version policy or review lifecycle.

### Change

MBT can regenerate tests after models change. The review identifies context awareness, dynamic
evolution and model synchronization as open challenges rather than solved capabilities.

### Automation

The automation boundary is model-to-test. Test-model construction, security-property modelling,
adapter development, testbed configuration and result interpretation remain partially manual.

### Human review

Human judgment remains necessary to assess model adequacy, security relevance, test oracles,
environmental validity and the meaning of a passed or failed execution.

## Documentation-first classification

### Classification

`model_required`

Documents and requirements may be inputs to model construction, but a formal or semi-formal test
model is required before the reviewed generation techniques operate.

### Nine documentation-first fields

1. Input and quality: requirements/specifications/SUT plus a security-enriched test model; document quality is not defined.
2. Compatibility: `model_required`.
3. Intermediate representation: UML/OCL, timed automata, CPN, BPMN, DFD, attack tree, topology graph, MACM or learned FSM.
4. Procedure: model construction, criterion definition, abstract generation, concretization, execution and review.
5. Output: abstract tests, scripts, execution observations, conformance or vulnerability evidence.
6. Provenance, uncertainty, review: partial model-to-test links; no common document provenance, confidence or review state.
7. Evolution/change: regeneration is possible in principle; dynamic and context-aware synchronization remains open.
8. Evaluation/evidence: Rapid Review of 17 mostly exploratory studies.
9. Thesis use: model-to-test architecture and evidence boundary; not proof of completeness or maturity.

## Directly supported

- MBST derives security-focused tests from explicit models.
- Security properties enrich functional or system models.
- Attack models and threat templates can guide test generation.
- Test-selection techniques depend on model formalism.
- Abstract tests require concrete translation and adapters.
- Model checking and MBST can be combined while remaining distinct evidence types.
- MBST can be combined with fuzzing, penetration testing and model learning.
- The reviewed evidence covers only part of the adopted attack taxonomy.
- IoT heterogeneity, model complexity and dynamic evolution remain open problems.
- Most included studies are exploratory.

## Not supported

- MBST guarantees system security.
- A passed generated suite proves absence of vulnerabilities.
- Model coverage equals attack coverage.
- The reviewed attacks are complete.
- Test models are derived automatically from heterogeneous documentation.
- Model checking and test execution are equivalent.
- Adapter translation is semantically lossless.
- The reviewed approaches are mature at industrial IoT scale.
- IoT results automatically generalize to all software domains.
- The review describes the 2026 tool landscape.

## Eight DDTA evidence questions

1. Documents sufficient without code: no; the approaches need a test model, though requirements or specifications may inform it.
2. Neutral intermediate representation: not defined; multiple formal and semi-formal projections are used.
3. Extracted versus inferred: not represented.
4. Method as overlay: security properties, attack models, test purposes and generators behave as specialized overlays.
5. Provenance, confidence, review: model-to-test links exist locally; no common governed provenance or confidence states.
6. Documentation change: not evaluated end to end; dynamic model evolution is an explicit gap.
7. Later code evidence: yes, through concretized test execution on a SUT, but adapters and oracles require governance.
8. Measurement: model coverage, selected attack coverage and execution results; no global completeness or strong industrial comparison.

## Relationship with Documentation-Driven Threat Analysis

### Base Analysis implications

A neutral Base Analysis should preserve enough governed facts to generate test-oriented projections:

- actors, components, devices and services;
- operations and messages;
- protocols and interfaces;
- states, transitions and temporal constraints;
- preconditions and postconditions;
- security properties and requirements;
- trust boundaries and deployment context;
- attacker actions and attack paths;
- technologies, versions and controls;
- source provenance and uncertainty.

### MBST plugin implications

An MBST plugin should declare:

- accepted projection and schema version;
- required security properties;
- attack-model or threat-template schema;
- test-selection criterion and coverage semantics;
- generator and version;
- abstract-test schema;
- concretization strategy;
- adapter and target-environment contract;
- oracle and verdict semantics;
- expected and observed evidence;
- unsupported conditions and deferred cases.

### Test lifecycle

```text
security property accepted
-> test model ready
-> abstract test generated
-> concretization pending
-> executable test ready
-> execution passed | failed | blocked | inconclusive
-> result reviewed
-> evidence accepted or rejected
-> rerun after model, adapter, SUT or environment change
```

DDTA must not silently translate a generated test or a passing verdict into a claim of complete
security.

## Candidate thesis claims

Supported directly or conditionally:

- Model-derived security testing requires explicit test models and security objectives.
- Abstract tests, concretized tests and execution evidence are distinct governed artifacts.
- Adapter and oracle semantics affect the meaning of test evidence.
- Model coverage and attack coverage require separate declarations.
- MBST can provide implementation-level evidence after a documentation-primary analysis.
- Dynamic evolution and synchronization are necessary for continuous security testing.

Not supported:

- DDTA can generate correct executable tests from ordinary documents without modelling.
- Passing generated tests proves system security.
- One formalism can support every security objective.
- IoT MBST evidence proves maturity across every software domain.
- Combining testing strategies guarantees completeness.
- Automated regeneration guarantees that models and the SUT remain synchronized.

## Research gap left open

The review starts from security-enriched models. It does not explain how heterogeneous,
versioned project documentation becomes a trustworthy test model, how each constraint retains
assertion-level provenance, how abstract tests are concretized without semantic loss, how
oracles are validated, or how adapters, models, documentation, implementation and runtime
environments remain synchronized.

The evidence base also lacks large realistic comparative studies, common coverage semantics and
strong measurements of defect detection, false positives, effort, scalability and accepted
security evidence.
